# Feature Specification: AI Plugin Creation Wizard

**Feature Branch**: `006-ai-plugin-wizard`

**Created**: 2026-08-24

**Status**: Draft

**Input**: User description: "AI plugin creation wizard: generate and trial-run download/metadata/login plugins from a description of the target site (GitHub issue #78) — the wizard starts from a site domain: the user enters a domain, the system automatically looks up which plugins are already installed for it (identifying which of the login/metadata/download types already exist, per each installed plugin's own declared matching rule), and asks the user which of the missing types they want to create (multi-select, up to three; types that already exist cannot be recreated). After the user supplies a page-feature description for each type to be generated, AI generates the corresponding `.ts` plugin code using the plugin SDK docs and same-type samples as reference. If both a login type and at least one metadata/download type are being created in the same run, the metadata/download plugin's actual dependency on the login state must be confirmed explicitly first — only when dependency is confirmed does a generation-order dependency get established (the login plugin is generated and trial-run successfully first) along with an association declaration; types that don't depend on login are handled independently and never forced into that binding. After generation, the system automatically performs a real trial run against the specific page(s) the user supplied under the target domain and shows the result or error; the user can hand-edit the code and re-run the trial, or have AI auto-fix it based on the error (up to 3 times, with every round's history kept for review/rollback). Aimed at logged-in maintainers/self-hosters; not a public-facing feature."

## Clarifications

### Session 2026-08-24

- Q: Are the test login credentials (account/password, etc.) a user supplies for the login type ever sent to the external LLM service? → A: No — credentials are never sent to the LLM. The real login request is executed locally; the AI only ever sees the success/failure outcome and a sanitized error message, never the credential values themselves.
- Q: When AI auto-fix hits its 3-attempt cap, what does "guide the user toward manual editing or revising the description to start over" actually mean? → A: It does not clear that type's prior draft history — it only means the "AI auto-fix" action becomes unavailable for that type once the quota is spent; the user can still revise the page-feature description and manually trigger a new generation round, which is appended as a new draft revision, with all history remaining viewable/revertible.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Look up existing plugins by domain and choose which types to create (Priority: P1)

As a self-hosted user who wants to add plugin support for some site, I want the wizard to first check whether that site already has plugins and which types are still missing, instead of making me dig through the plugin list from memory or risk generating something that duplicates or conflicts with what already exists.

**Why this priority**: This is the entry point and precondition for the entire wizard flow — without it, a user could either reinvent the wheel (the site may already have a login plugin) or generate an orphaned metadata/download plugin that misses a login capability it should have been associated with. Every later generation/validation step is built on "the user knows exactly what this site is currently missing."

**Independent Test**: Given a domain, the wizard accurately reports, for each of the login/metadata/download types, whether an installed plugin already covers this domain or the type is missing, and only allows the user to select generation targets from the missing types (existing types cannot be selected).

**Acceptance Scenarios**:

1. **Given** the wizard's initial page, **When** the user enters a domain and submits the lookup, **Then** the system displays the current status of each of the login/metadata/download types for that domain (covered by an existing plugin / missing), with covered types clearly marked and not selectable for generation again.
2. **Given** the lookup shows some types are missing, **When** the user selects one or more (up to three) of the missing types as this run's generation targets, **Then** the system collects a page-feature description for each selected type, to be used for generation.
3. **Given** all three types already have a corresponding plugin for this domain, **When** the lookup completes, **Then** the system clearly states "this domain already has full plugin coverage, nothing to create" and offers no selectable generation target.
4. **Given** the user's selection this run includes both "login" and at least one of "metadata"/"download", **When** the user fills in the page-feature description for the metadata/download type(s), **Then** the system asks, separately for each metadata/download target, "does this function require login to work correctly", rather than defaulting to "login was selected, so every other type depends on it."

---

### User Story 2 - Generate usable plugin code from a description (Priority: P1)

As a user who has already decided which plugin types to generate, I want to only describe the site's page features (how to identify download links/metadata fields) and have the system generate working plugin code for me, without needing to learn the SDK docs from scratch or copy an existing plugin's structure. I don't expect AI to guess the page structure purely from my text description — if it needs to see what the real page actually looks like to generate more accurately, the system should be able to fetch that for it and feed the result back, rather than making generation quality entirely dependent on how precisely I happened to describe things.

**Why this priority**: This is the core value the wizard exists to deliver — without it, everything the wizard does up to this point (lookup/selection) produces no actual output. Every other capability (trial run, manual edit, AI fix) exists to validate/iterate on this step's result.

**Independent Test**: Given a confirmed target type (e.g. "metadata") and its page-feature description, triggering generation produces a `.ts` draft with a correct `pluginInfo()` structure and the matching type-specific entry function (e.g. `execMetadata`), and this code passes the plugin system's basic legality check on its own (this step is considered complete independent of whether a later trial run succeeds). During generation the system actually visits the target page as AI requests and feeds the result back to AI to continue processing; this process is not required to be visible to the user in real time. If this type is marked as login-dependent, the generated result must include an association declaration pointing at the corresponding login plugin.

**Acceptance Scenarios**:

1. **Given** the user has filled in a page-feature description for a target type and submitted for generation, **When** the system invokes AI to generate, **Then** the system returns, within a reasonable wait, a structurally complete plugin draft whose type-specific entry function matches the target type.
2. **Given** AI determines during generation that it needs to see the real content of the target page to generate accurately (rather than relying solely on the user's text description), **When** AI raises this access request, **Then** the system actually performs that access, feeds the result back to AI to continue, and ultimately shows the user only the fully generated code draft — the user is not required to be involved in this intermediate process.
3. **Given** the user submits a generation request with an overly terse description, **When** the system invokes AI to generate (including cases where AI proactively requests to access the page for more information), **Then** the system still returns a code draft (even if the trial run is very likely to fail), rather than outright rejecting the submission or aborting with an error — the trial-run step is left to surface the problem.
4. **Given** the LLM service is not configured (no API key set) or the call fails, **When** the user submits a generation request, **Then** the system clearly states "AI generation unavailable" with the specific reason, and no plugin file is left behind.
5. **Given** this run generates both a login type and a metadata/download type marked "login-dependent", **When** the system generates in order, **Then** the login type must finish generating and pass at least one successful trial run before generation of the dependent metadata/download type begins, and the generated result automatically carries an association declaration pointing at that login plugin; types that don't depend on login are not subject to this ordering and can be processed independently.

---

### User Story 3 - Trial-run to validate the generated result (Priority: P1)

As a user who already has an AI-generated plugin draft, I want to immediately run a real call against a real page and see plainly whether this code actually works, rather than having to manually drop the code into the plugin directory and trigger it from somewhere else. For metadata/download types, I'd rather test against more than one page, because a plugin can easily happen to fit only the one page I referenced while describing it, and fail on a different entry due to subtle page-structure differences — testing a single page doesn't give me enough confidence.

**Why this priority**: Generated code cannot prove its own correctness (AI hallucination and misreading of page structure are the norm). Without trial-run feedback, the user only has a piece of text that "looks like a plugin" with no way to tell if it actually works, which would make the entire wizard pointless — this is, together with User Story 2, one of the two inseparable parts of the MVP.

**Independent Test**: Given a plugin draft from any origin (AI generation / hand-written by the user / result of a previous fix round): for a metadata or download type, given at least three distinct target page links; for a login type, given a set of test login credentials (no "number of page links" involved). Triggering a trial run makes the system show a clear "success" (with the data the plugin actually returned) or "failure" (with a specific error) outcome — for metadata/download types, a result is given separately per link — and this trial run leaves no permanent trace in the plugin system (it does not appear in the list of real, installed plugins).

**Acceptance Scenarios**:

1. **Given** a metadata or download type plugin draft, **When** the user supplies at least three distinct target page links and clicks "trial run", **Then** the system triggers one real call per link and shows each link's own result, one by one, within a reasonable wait.
2. **Given** a login type plugin draft, **When** the user supplies test login credentials and clicks "trial run", **Then** the system triggers one real login call and shows the result, without requiring multiple "page links".
3. **Given** a trial run call succeeds, **When** the result comes back, **Then** the user can see the specific content the plugin actually identified/extracted (e.g. metadata field values, the list of download links, the post-login cookie state), not just a generic "success" message.
4. **Given** some of the multiple links supplied for a metadata/download type succeed and others fail, **When** the results come back, **Then** the user can clearly tell which links failed and each one's specific error reason, without a single overall pass/fail verdict masking the individual link-level problems.
5. **Given** a trial run call fails (network error, code logic error, timeout, etc.), **When** the result comes back, **Then** the user can see the specific error reason, and the failure does not affect any other currently running plugin.
6. **Given** the user has not yet done any trial run and wants to directly commit the current draft, **When** the user attempts to confirm-save, **Then** the system requires at least one trial run to have completed first (for metadata/download types, results must exist for every supplied link, regardless of outcome; for login types, a result must exist) before allowing the save, so that unvalidated code never goes straight into the plugin directory.

### User Story 4 - Manually edit the code and re-validate (Priority: P2)

As a user with some code-reading ability who doesn't want to write everything from scratch, I want to directly modify the AI-generated code in the interface (e.g. tweak a selector, add a field) and immediately re-run the trial to see the effect, without exporting a file, editing it in a local editor, and figuring out how to get it back in.

**Why this priority**: AI generation results are never going to nail it every time, especially for sites with complex page structures or underspecified descriptions. Manual tweaking is a more precise, LLM-call-frugal way to fix things than "regenerate the whole thing", and is a key part of turning the wizard from a "one-shot lottery" into an iterative tool — but even without this capability, the core "generate → trial-run → see result" loop of User Story 2+3 is already usable on its own (the user can keep regenerating the whole draft to iterate by trial and error), so this stays below P1.

**Independent Test**: Open an already-generated code draft, directly modify some part of it in the editing area and save the change, and trigger a new trial run against the modified code without leaving the wizard page.

**Acceptance Scenarios**:

1. **Given** an already-generated plugin code draft, **When** the user edits the code content in the editing area, **Then** the edit is kept as the current draft's latest state, without affecting any trial-run history already recorded for it.
2. **Given** the user's edited code has a syntax error, **When** the user triggers a trial run, **Then** the system clearly reports this as a "the code itself cannot be parsed/executed" error (distinct from a "runs but the logic is wrong" error), so the user doesn't have to figure out for themselves whether it's a network issue or a code issue.

---

### User Story 5 - AI auto-fixes a failed trial run (Priority: P2)

As a user who doesn't want to dig into TypeScript/DOM-selector details myself, I want a failed trial run to let AI look at the error and fix the code itself, instead of me having to copy the error text out somewhere and figure it out on my own.

**Why this priority**: This is an alternative fix path to "manual editing", aimed at users who don't have the ability to read/modify code, or who simply want to let the system try once first. It lowers the barrier for a non-technical user to walk the full "generation failed → get it fixed → put it to use" loop inside the wizard, but it is not a necessary condition for that loop to exist (a technical user can rely entirely on User Story 4's manual editing), so it's ranked P2 alongside manual editing.

**Independent Test**: Given a failed trial-run record (with error info) and the code at that time, triggering "AI auto-fix" produces a new code draft and automatically re-runs a trial against it, with no manual user intervention needed for any intermediate step.

**Acceptance Scenarios**:

1. **Given** a trial run has failed, **When** the user selects "AI auto-fix", **Then** the system submits that failure's error info together with the current code to AI, produces a fixed new code draft, and automatically triggers a trial run against the new draft.
2. **Given** the trial run after an AI auto-fix still fails, **When** the user selects "AI auto-fix" again, **Then** the system keeps trying, but once the cumulative auto-fix count hits the cap, that action becomes unavailable, and the user is prompted to switch to manual editing, or to revise the page-feature description for that type and manually trigger a new generation round; the history accumulated for that type up to that point is not cleared as a result.
3. **Given** multiple rounds of generation/fixing have already happened, **When** the user views the history, **Then** the user can see each round's code content and corresponding trial-run result (success/failure with detail), and can choose to set any round's code as the currently active draft.
4. **Given** the user is already satisfied with the result partway through auto-fixing, **When** the user chooses to confirm-save, **Then** the system does not require exhausting the auto-fix count or returning to the latest round first — the user can directly commit whichever round they've selected.

---

### User Story 6 - Confirm-save the generated plugin (Priority: P1)

As a user satisfied with the trial-run result, I want a clear "confirm to use" action that actually turns this code into a plugin usable within the system, rather than leaving it stuck as a draft inside the wizard forever.

**Why this priority**: Without this step, all the preceding generation/validation/fixing work is just a one-off demonstration that the user can never actually put to use — this is the final step that turns the whole wizard from an "experimentation tool" into something that "actually produces a new plugin", and is an indispensable part of the MVP.

**Independent Test**: Given a code draft that has completed at least one trial run, triggering confirm-save turns it into a plugin that can subsequently be called normally like any other plugin, with clear success/failure feedback throughout the process.

**Acceptance Scenarios**:

1. **Given** a code draft that has been trial-run, **When** the user confirms save, **Then** the system validates that the code is legal (correctly recognized as the declared plugin type), and on passing validation makes it a real, installed plugin in the system.
2. **Given** the plugin namespace the user is trying to save conflicts with an already-installed plugin in the system, **When** the user confirms save, **Then** the system clearly reports the conflict, does not overwrite the existing plugin, and lets the user rename and retry.
3. **Given** any error occurs partway through the save process (validation failure, write failure, etc.), **When** the error occurs, **Then** the system guarantees no incomplete/corrupted plugin file is left behind, the draft's state within the wizard is unaffected, and the user can keep working on it in the wizard.

---

### User Story 7 - Add a login plugin afterward, based on an AI suggestion following a failed trial run (Priority: P2)

As a user who didn't select the login type at the start (because I wasn't sure whether this site needed it) and only generated a download or metadata plugin, I want a failed trial run to help me figure out whether the failure is due to missing login state — and if so, directly guide me to generate a login plugin as a follow-up, then automatically associate it back to the failed plugin, without me having to go back and redo the whole wizard flow with the login type selected this time.

**Why this priority**: It's genuinely hard for a user to correctly judge, at the initial description stage, whether a site needs login. "Try the download/metadata plugin first, and only figure out whether login is missing after it fails" better matches real usage habits than "requiring the user to have it all figured out up front." This is an important reinforcement of the P1 core loop (generate → trial-run → feedback), but it isn't a necessary condition for that loop to exist — without this path, the user can still achieve a similar effect by starting a new domain lookup and selecting the login type this time, just more tediously — so it's P2.

**Independent Test**: Given a failed download/metadata trial-run result, hand it to AI to judge whether the failure might be login/permission related; if so, the system offers a "add a login plugin" suggestion entry point, and after the user accepts and completes generating and validating the login plugin, the system automatically updates the previously failed draft to associate with this login plugin (or with an already-existing login plugin for this domain), and lets the user re-trigger a trial run for the originally failed link(s) using the new association.

**Acceptance Scenarios**:

1. **Given** a download or metadata type trial run has failed, **When** the system hands the error info to AI for judgment and AI concludes the failure might be login/permission related, **Then** the system proactively tells the user "this failure might require login to resolve" and offers a "generate a login plugin" entry point.
2. **Given** AI judges the failure to be unrelated to login (e.g. a plain network timeout, a wrong selector), **When** the trial run fails, **Then** the system does not proactively suggest adding a login plugin, avoiding an irrelevant interruption.
3. **Given** the user accepts the "generate a login plugin" suggestion, and no login plugin previously existed for this domain, **When** the user supplies test credentials for the login type and completes generation and a successful trial run, **Then** the system automatically updates the previously failed download/metadata draft to carry an association declaration pointing at this new login plugin.
4. **Given** a login plugin already exists for this domain at lookup time (not regenerated this run), **When** AI judges that a download/metadata trial-run failure might be login related, **Then** the suggestion is to associate directly with this existing login plugin, not to guide the user into generating a duplicate new one.
5. **Given** the login association has been established, **When** the user re-triggers a trial run on the previously failed download/metadata draft, **Then** the system re-triggers the call for the originally failed link(s) using the new login association.

### Edge Cases

- The target site the user describes needs login state to access its content, but the user didn't select the login type at the start — expected to go through User Story 7's recovery path, rather than requiring the user to correctly predict this at the initial stage.
- The user switches the plugin type mid-session (e.g. picks "metadata" first, generates a version, then switches to "download") — the prior generation/trial-run history should be treated as no longer applicable to the new type, so the user doesn't mistakenly mix history drafts from different types together.
- The content AI's generation or fix returns is not legal, parseable code (e.g. AI outputs a natural-language explanation instead of pure code, or the code has an outright syntax error) — the system needs to recognize this as a "generation failure" rather than presenting this invalid content as a usable draft to the user.
- One of the target links the user supplied is itself unreachable or returns unexpected content (404, CAPTCHA block, etc.) — the trial-run failure message should reflect that "the target page itself has a problem", not a plugin code logic error, so the user isn't misled into editing code that was already correct; this is a different class of failure from "needs login", and AI's judgment needs to be able to tell them apart.
- The user triggers a new generation/fix/edit action while a trial run is still in progress — the system needs a clear, predictable way of handling this (e.g. disallowing concurrent operations, or letting the new operation supersede the old one), so the two results don't overwrite each other and leave the UI state in a broken condition.
- The user isn't interested in the "add a login plugin" AI suggestion (e.g. they've already confirmed the site genuinely doesn't need login and the trial-run failure has some other cause) — the user must be able to dismiss the suggestion and keep handling it another way (manual editing / AI auto-fix of the code itself), and must never be forced into the login-supplement flow.
- The system encounters more redirects than the cap allows while accessing a target address (e.g. a redirect loop, or an overly deep redirect chain from misconfiguration) — this access attempt must be judged a failure and reported to AI as-is, rather than letting the request follow redirects indefinitely.
- An auxiliary reference URL the user supplied for a target type is itself unreachable, or its content contradicts the page-feature description — this must not cause the overall generation to fail; AI weighs its reference value at its own discretion, and how to weigh it is squarely AI's judgment call, not something the system needs to pre-filter or validate.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The system MUST provide a wizard-style interface that lets a logged-in user enter a target domain and trigger a lookup.
- **FR-002**: Based on the domain entered per FR-001, the system MUST look up installed plugins in the system and report, for each of the login / metadata / download types, whether an existing plugin already covers this domain.
- **FR-003**: If all three types are already covered, the system MUST clearly tell the user "this domain already has full plugin coverage, nothing to create" and MUST NOT offer any generation entry point.
- **FR-004**: If some types are missing, the system MUST only allow the user to select one or more (up to three) of the missing types as this run's generation targets, and MUST NOT allow selecting a type that's already covered.
- **FR-005**: For metadata/download types, the system MUST collect at least three distinct target page links (used both to drive AI's own page-structure investigation during generation and for the later multi-link trial run); for the login type it collects test login credentials and does not require page links. The system MUST NOT require a free-text page-feature description from the user — real page content, fetched by AI itself during generation, is the source of truth for selector/field-extraction logic, not a user's manual description of the page (a design simplification made after initial implementation: the field existed and was removed, since it duplicated information AI can obtain more reliably on its own via `fetch_page`).
- **FR-006**: The system MUST let the user optionally supply one or more auxiliary reference URLs for each target type (e.g. the site's own API/JSON endpoint address) for AI to consult during generation; omitting them MUST NOT block the generation flow from proceeding normally.
- **FR-007**: If the user's selection this run includes both "login" and at least one metadata/download type, the system MUST ask, separately for each metadata/download target, "does this depend on login to work correctly" — it MUST NOT assume every other type depends on login just because login was selected.
- **FR-008**: The system MUST be able to generate, via AI, a plugin code draft for each target type based on the information the user supplied; the draft MUST structurally follow the plugin system's existing conventions for that type (e.g. declaring namespace, type, and the corresponding entry function). A metadata/download draft marked "login-dependent" MUST include, in its generated result, an association declaration pointing at the corresponding login plugin.
- **FR-009**: When AI generates or fixes code, the system MUST provide AI with the type/interface definitions for plugin development, plus, if this domain already has an installed plugin of a *different* type (e.g. generating "metadata" for a domain that already has a "download" plugin), that other plugin's own source code as a reference sample — a same-domain plugin's URL-matching/page-parsing approach is relevant regardless of its specific type, and the target type itself can never have an existing sample in the first place (FR-004 only allows selecting types the domain lookup found missing). Generation MUST still proceed normally when no such sample exists for this domain, and MUST NOT fail merely for lacking one.
- **FR-010**: The responsibilities of the system and AI MUST be clearly separated — the system (local) is only ever responsible for actually performing network access/trial-run calls and faithfully forwarding the raw result; it MUST NOT perform its own heuristic classification or semantic judgment on the result (e.g. guessing "does this need login" via keyword/status-code matching). All semantic-level understanding, classification, and decision-making (what code to generate, why a trial run failed, whether login is needed, etc.) MUST be done by AI. When AI determines it needs more information to proceed (e.g. it needs to see the real content of the target page first, or needs the user to supply authentication information), AI MUST explicitly state this access/information request, which the system is then responsible for actually carrying out or collecting from the user, and must feed the result back to AI to continue processing. This "system executes — AI judges — proposes the next request" loop applies throughout every AI-touching part of the wizard, including code generation and diagnosing why a trial run failed; the loop's intermediate steps are not required to be visible to the user in real time — the user only needs to see each round's final output (a code draft or a clear judgment conclusion).
- **FR-011**: When the system performs an access and the target address returns a redirect, it MUST automatically follow it through to completion, and MUST NOT interrupt the flow to wait for an extra decision just because one redirect occurred; however, it MUST supply AI with the full redirect trail from that access (the original address, every intermediate hop, and the final landing address) together with the final page content — it MUST NOT hand AI only the final page content while discarding the redirect trail itself, since the trail can itself be an important signal for later judgments (e.g. whether login is required). The number of redirects a single access automatically follows MUST be capped; once the cap is exceeded, the system MUST stop following further, judge this access a failure, and supply AI with the full redirect trail accumulated so far (including the fact that "the redirect cap was exceeded before reaching a final page") as-is, rather than following indefinitely and leaving the request hanging or stuck in a redirect loop.
- **FR-012**: Test credentials (account/password, etc.) a user supplies for the login type MUST NEVER be sent to the AI/LLM service — the login type's trial-run call MUST be executed entirely locally by the system (reading the credentials, constructing the login request, making the real call); AI, in this step, may only ever access the call's outcome (success/failure status, a sanitized error message), and MUST NOT be given the plaintext credential values themselves. When AI generates/fixes login-type code, it operates only on the code-logic layer of "how to read the credentials from parameters, how to use them to construct the request" — it likewise does not need, and MUST NOT be given, the specific credential values.
- **FR-013**: If this run generates both a login type and a metadata/download type marked as login-dependent, the system MUST finish generating the login type and pass at least one successful trial run for it before beginning generation of the dependent metadata/download type's code; types that don't depend on login are not subject to this ordering and can be processed independently, and MUST NOT be forced to queue behind the login type just because a login type exists in the same batch.
- **FR-014**: The system MUST support triggering a real trial run against any code draft (whether from AI generation, AI fix, or manual user editing): a metadata/download draft MUST trigger a call for every link the user supplied and return, one by one, a clear success (with the actual result data) or failure (with a specific error reason) for each; a login draft triggers one call against the supplied test credentials and returns the corresponding outcome.
- **FR-015**: The trial-run process MUST be isolated/protected to the same degree as the runtime environment for the system's real, installed plugins (a draft trial run must not affect any other real plugin's operation, and a draft must not gain any permission beyond what it itself declares).
- **FR-016**: The system MUST let the user directly modify the current code draft's content inside the wizard interface, and MUST let a modification immediately trigger a new trial run against the new content, without needing to export/import a file.
- **FR-017**: The system MUST support an "AI auto-fix" action: submit the most recent trial run's error info (for a metadata/download type, this may include per-link errors across multiple links) together with the code at that time to AI, produce a new fixed code draft, and automatically trigger a trial run against the new draft.
- **FR-018**: Within a single wizard session, the number of consecutive AI auto-fix attempts for the same target type MUST be capped (3); once the cap is reached, the system MUST stop auto-continuing and make the "AI auto-fix" action unavailable for that type, clearly inform the user the cap has been reached, and guide them toward manually editing the code, or revising that type's page-feature description and manually triggering a new generation round; the history accumulated for that type up to that point MUST NOT be cleared as a result of hitting the cap — a new round is appended as a new draft revision, viewable/revertible just like the existing history (see FR-019).
- **FR-019**: The system MUST retain every generation/fix round's code content and corresponding trial-run result, per target type, within a single wizard session; the user MUST be able to view any historical round and set any one of them as the currently active draft (there is no requirement to always use the latest round).
- **FR-020**: The system MUST provide, per target type, a clear "confirm-save" action that turns the user's selected draft for that type into a real, installed plugin in the system; before saving, it MUST require that this draft has completed at least one trial run (for metadata/download types, results must exist for every supplied link; for login types, a result must exist), regardless of the outcome.
- **FR-021**: If the target plugin namespace conflicts with an already-installed plugin at save time, the system MUST reject the overwrite, clearly report the conflict, and let the user rename and retry.
- **FR-022**: If any step of the save process fails, the system MUST guarantee no incomplete or corrupted plugin file is left behind, the draft's state within the wizard MUST remain unaffected, and the user MUST be able to continue working on it.
- **FR-023**: The system MUST restrict this feature to logged-in users only; users who are not logged in MUST NOT be able to access it.
- **FR-024**: When the service AI generation/fixing depends on is unavailable (e.g. no access credential configured, call failure), the system MUST give a clear reason, MUST NOT leave any plugin file behind, and MUST NOT affect any draft/history state already present in the wizard.
- **FR-025**: The system MUST support an "add a login plugin" path: when a metadata/download trial run fails and AI judges the failure might be login/permission related, the system offers an entry point to generate a supplementary login plugin; once the user completes generating, validating, **and confirm-saving** that login plugin, the system MUST automatically offer to update the previously failed draft to associate with this login plugin (or, if a login plugin already exists for this domain, associate directly with the existing one instead of generating a duplicate). The confirm-save step is required before association (not merely a passing trial run) because the association is a `login_from` reference to a real, resolvable plugin namespace (FR-008) — a draft still sitting in the trial-run staging area has no such namespace yet, only a throwaway one that won't exist once the trial run's own staged file is cleaned up.
- **FR-026**: Every plugin file the wizard generates (via AI generation, AI auto-fix, or a manual edit made from within the wizard) MUST carry a persistent, machine-readable marker identifying it as wizard-created — written into the plugin source file itself (not a separate database/Redis record), so the marker survives independently of the wizard session and is visible to anything that later reads the plugin file directly (the plugin management page, a manual file inspection, an export). The marker MUST NOT be lost or need to be re-derived once the file exists on disk.
- **FR-027**: The system's plugin management page (where already-installed plugins are listed) MUST visually distinguish a wizard-created plugin (per FR-026's marker) from a hand-written/manually-uploaded one, at a glance, without requiring the user to open the file.
- **FR-028**: The system MUST let the user export an installed plugin (wizard-created or not) as a downloadable `.zip` archive containing that plugin's own `.ts` file, from the plugin management page.
- **FR-029**: Within the wizard itself, the current state of each target type MUST be visibly distinguished as either "draft" (not yet confirm-saved — FR-020) or "official" (confirm-saved, now a real installed plugin per FR-026's marker) at every point in the session, not only at the moment of saving.
- **FR-030**: A confirm-saved plugin (FR-020) is written to the same plugin directory (and subject to the same persistence characteristics) as any other installed plugin — the wizard does not introduce a separate storage location or persistence guarantee of its own. In particular: when the deployment has the plugin directory mounted from the host (the standard development setup, and any production deployment that explicitly mounts a host path over it), the saved file is immediately present on the host and survives container recreation; when the plugin directory is *not* host-mounted (a plain container run using the image's baked-in `plugins/` copy), the saved file exists only inside that container's writable layer and is lost if the container is removed/recreated (though it survives ordinary restarts) — the system MUST NOT claim or imply a stronger persistence guarantee than the deployment actually provides, and FR-028's export capability exists in part to let a user in this second case get the file out before that risk applies.
- **FR-031**: Because the system cannot reliably determine at runtime whether its plugin directory is host-mounted or ephemeral (FR-030 — both appear as an ordinary writable directory from inside the running process), the system MUST show a persistence reminder — pointing the user at FR-028's export action — every time a confirm-save (FR-020) succeeds, rather than attempting to detect and suppress it only for the ephemeral case. The reminder MUST NOT block or delay the save's own success feedback; it is an additional, dismissible notice alongside it.

### Key Entities *(include if feature involves data)*

- **Wizard Session**: The container for one use of the wizard — holds the target domain the user initially entered, that domain's plugin-lookup result, the set of target types the user selected, and, per target type, its page-feature description/auxiliary reference URLs/test material (links or credentials), its login-dependency flag, and its generation/fix rounds. The session ends/resets when the user leaves the wizard or explicitly starts a new lookup.
- **Domain Lookup Result**: The output of one domain lookup — for each of the login/metadata/download types, either "covered (which installed plugin it maps to, including that plugin's own code, which can serve as a reference sample when generating another type for the same domain)" or "missing".
- **Draft Revision**: One independent version within a given target type's generation session — holds that version's code content, how it was produced (AI generation / AI auto-fix / manual user edit), and the set of trial-run results triggered against it (possibly empty, if never trial-run). Multiple draft revisions are ordered by when they occurred, and the user can switch between them.
- **Trial Run Result**: One real call record, belonging to a draft revision. For metadata/download types, one "trial run" holds an independent success/failure status per target link, the actual returned data on success (including the full redirect trail that actually occurred), and the specific error reason on failure. For login types, it holds the success/failure status and detail of the single login call.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: For a site where some plugin types are already installed for the same domain, the user can tell at a glance, right after the lookup, which types are still missing, without accidentally generating a duplicate of an already-existing type.
- **SC-002**: For a target site with clear, well-structured download links/metadata patterns, the user can get a metadata/download type to trial-run successfully against every supplied test link within no more than 3 generation/fix iterations.
- **SC-003**: The user can go from opening the wizard to successfully saving a working set of plugins without ever needing to consult the plugin SDK docs or look at an existing plugin's source.
- **SC-004**: Every trial-run operation (including each link in a multi-link scenario) shows the user a clear success or failure result within a reasonable wait — there is no "stuck with no feedback" situation.
- **SC-005**: No generation, trial-run, or save failure ever results in an existing, real plugin in the system being unexpectedly overwritten, corrupted, or left as an incomplete file.
- **SC-006**: Within a single wizard session, the user can revisit any prior round's code and result at any time and choose to continue from it, without ever losing historical output.
- **SC-007**: When a user generates both a login type and a metadata/download type that depends on it, the resulting metadata/download plugin genuinely works without requiring manual user intervention for login; types that don't depend on login are never made to wait needlessly for the login type to finish.

## Assumptions

- The target site does not require handling sophisticated human-verification challenges (e.g. interactively solving a CAPTCHA) — a plugin generated for such a scenario will very likely fail its trial run, which is an accepted, expected boundary of this feature's capability and is not specially handled here.
- The user has the basic ability to judge "does this trial-run result match what I expected" (e.g. they can tell whether the returned tags/links are what they actually wanted) — the system is only responsible for faithfully displaying the raw trial-run result, not for judging semantic correctness on the user's behalf.
- The user is able to supply, for a metadata/download type, at least three real, valid target links that actually represent that site's typical page structure (e.g. detail pages for different works/entries on the same site), rather than three near-identical links that don't reveal any structural variation.
- The draft revisions produced in one wizard session only need to remain available for that session's own lifetime — there is no requirement to persist the full history across sessions (e.g. across a browser refresh); only the code that's ultimately confirm-saved needs to be persisted long-term as a real plugin file.
- This feature is aimed at logged-in users (consistent with the requirements for other plugin-management actions), and does not distinguish any finer-grained role/permission (e.g. a separate "plugin management" permission) — it reuses the existing login-state check as-is.
- Credential configuration for the LLM service AI generation/fixing depends on reuses the system's existing mechanism; this feature does not introduce a new credential-management UI.
- Regenerating and replacing an already-existing plugin via AI from within the wizard is not supported — any type the domain lookup finds already covered is always marked unselectable; if a user needs to replace an existing plugin, they need to go to the existing plugin-management UI and handle it manually, which is out of scope for this feature.
