# Feature Specification: 删除安全网（删除台账 / 自动快照 / 批量删除守卫 / 库目录诊断）

**Feature Branch**: `028-deletion-safety-net`

**Created**: 2026-11-23

**Status**: Draft

**Input**: User description: "清理误操作留下的数据之后，把「删除安全网」做成一套完整机制：所有档案记录删除都留台账可撤销、自动生成并保留数据库快照、批量删除要守卫、库目录异常时日志与任务里带上诊断信息。用 speckit 从 specify 走到 implement，一个 PR 交付。"

## 背景与动机

2026-11-23 本机发生了一次真实的数据损失事故：一个实例连到了另一套数据库、同时又指向了不同的库目录，随后库里大批档案记录被清掉（`file` 字段被清空，第二遍清理直接永久删除），接着一次全库扫描把它们重新收录成了**空标签的新记录**。全过程没有任何一处留下可撤销的记录，也没有任何一份可回退的备份——Redis 的 AOF 忠实地把删除也持久化了。

事后复盘确定了三件事：

1. **删除路径不止一条**：Clean Database、单条删除、修订版取代、拆分原始档等内部清理，最终都调用同一个永久删除动作；现有的回收站只覆盖「用户主动删除的那一条」。
2. **没有任何台账**：记录一旦删除，标签、阅读进度、分类归属全部不可恢复。
3. **备份全靠人点**：只有手动导出的 JSON 备份；周期性任务里没有备份，破坏性操作前也不备份。

因此本特性的目标不是修某一条具体路径，而是给**删除这个动作本身**装上安全网。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 删掉的档案能找回来 (Priority: P1)

运维在设置页点了「清理数据库」，或在别处触发了批量清理。事后发现库里少了几百个档案、标签和阅读进度都没了。他打开设置页的备份区，看到「最近删除」列表里有刚才那批记录，点「恢复」，记录连同标签、阅读进度、分类归属一起回到库里（文件还在磁盘上的那些立刻可用；文件确实不在的，标为待补文件）。

**Why this priority**: 这是唯一能在事故已经发生之后把数据救回来的能力，也是这次事故里唯一缺的一环。只做这一条，本次事故就能完全避免损失。

**Independent Test**: 删除任意一条档案记录（通过 Clean Database 或单条删除），随后在「最近删除」里恢复它，检查标签/进度/分类归属与删除前一致。

**Acceptance Scenarios**:

1. **Given** 库里有档案 A（带标签与阅读进度），**When** 通过 Clean Database 删除 A，**Then**「最近删除」里出现 A，且保存了删除前的完整信息。
2. **Given** A 在「最近删除」里且文件仍在磁盘上，**When** 恢复 A，**Then** A 重新出现在库里、可正常打开，标签与阅读进度与删除前一致。
3. **Given** A 在「最近删除」里但文件已不在磁盘上，**When** 恢复 A，**Then** A 的记录恢复、标记为「文件缺失」，并且不会因为这次恢复而破坏其它记录。
4. **Given** 台账里的一条记录超过了保留期，**When** 清理任务运行，**Then** 该条被清除，且不影响仍在保留期内的记录。
5. **Given** 删除的是单条档案（用户在阅读页删除），**When** 删除完成，**Then** 除了进入回收站的文件之外，记录本身也出现在「最近删除」里（两条路径不互相替代）。

### User Story 2 - 破坏性操作前和每天都有备份 (Priority: P1)

运维从不记得点「导出备份」。某天他发现数据不对，想回退到昨天的状态。系统在他没有做任何操作的情况下，已经留下了最近 7 天每天一份、以及最近 4 周每周一份的完整备份；他在设置页下载其中一份，或者直接用它恢复。

**Why this priority**: 台账只能覆盖「记录还在保留期内」的情况；如果问题发现得晚，唯一的兜底是更早的完整备份。

**Independent Test**: 让实例运行跨过一次「新的一天」，确认自动生成了一份当日备份；触发一次 Clean Database，确认操作前额外生成了一份备份；确认超出保留策略的旧备份会被清理。

**Acceptance Scenarios**:

1. **Given** 实例启动且当天还没有备份，**When** 启动完成，**Then** 磁盘上出现一份当天的备份文件，内容与手动导出的一致（可被恢复）。
2. **Given** 当天已有备份，**When** 实例重启，**Then** 不重复生成第二份当天备份。
3. **Given** 即将执行 Clean Database / 恢复导入 / 索引重建，**When** 操作开始，**Then** 先落一份「操作前」备份，失败不阻塞操作但会在任务结果里报告。
4. **Given** 备份数量超过保留策略，**When** 清理运行，**Then** 只保留 7 份每日 + 4 份每周，更老的被删除。
5. **Given** 设置页的备份区，**When** 打开，**Then** 能看到自动备份列表、下载任意一份、以及用其中一份恢复。

---

### User Story 3 - 危险的批量删除需要确认 (Priority: P2)

一次性删除会移除库中很大比例的记录（例如 Clean Database 要删掉 40%），系统停下来说「这次会删除 N 条（占 M%），请确认」，而不是直接执行。确认后可以继续；不确认则什么都不删。

**Why this priority**: 防止一次误操作就把大部分数据带走，属于「事前」保护；即使台账能救，也希望不要走到那一步。

**Independent Test**: 构造一个会让 Clean Database 删除超过阈值的库，触发操作，确认它被拒绝并给出可读的说明；带确认参数重试，确认它执行。

**Acceptance Scenarios**:

1. **Given** 一次清理将删除的记录数超过阈值，**When** 未确认就发起，**Then** 操作被拒绝，返回删除数量与占比，且没有删除任何记录。
2. **Given** 同样的操作带上显式确认，**When** 再次发起，**Then** 操作执行，且任务/日志里记下「已确认」。
3. **Given** 删除数量在阈值以内，**When** 发起，**Then** 直接执行，不打扰用户。
4. **Given** 阈值有默认值，**When** 运维在设置里调整，**Then** 新值立即生效，无需重启。

---

### User Story 4 - 库目录看起来不对时能立刻看出来 (Priority: P3)

扫描或清理之后，日志与任务详情里能直接看到「本次扫描到的文件数 / 数据库里记录数 / 能对上的比例 / 库目录在宿主机上的来源」，运维据此判断是不是挂错了目录，而不是靠猜。

**Why this priority**: 诊断不阻止损失，但能显著缩短发现时间；它也是前三条的辅助证据来源。

**Independent Test**: 用一个明显与数据库不匹配的库目录运行扫描，检查日志与任务结果里是否包含记录数、重合度、库目录来源。

**Acceptance Scenarios**:

1. **Given** 库目录与数据库记录明显不匹配，**When** 扫描完成，**Then** 日志里有一条包含「扫描文件数、记录数、重合度、库目录来源」的记录。
2. **Given** 运行环境拿不到挂载来源信息（例如非容器或某些容器运行时），**When** 扫描完成，**Then** 其它字段照常输出，缺失项明确标注为未知，不因此失败。
3. **Given** 一次清理删除了记录，**When** 查看任务结果，**Then** 能看到删除数、清空 `file` 的数、以及操作前后的记录总数。

### Edge Cases

- 台账写入失败（存储不可用）时：删除仍然执行，但必须在结果里明确报告「本次删除无法撤销」，不能静默。
- 台账保留期与单条删除并发：恢复正在被清理的条目时，以「先到先得」为准，失败要给出可读原因。
- 备份生成失败（磁盘满、权限）：不能阻塞启动或操作，但要在日志与设置页的状态里可见；当日不再重试以避免风暴。
- 备份文件被人工删除或损坏：列表里标记为不可用，恢复时给出明确错误。
- 库目录完全为空（卷没挂上）：已有保护（全部文件缺失时保留记录）保持不变。
- 同名档案在恢复时已存在（id 冲突）：跳过并报告，不覆盖现有记录。
- 记录数量非常大（十万级）时：台账与备份操作都不能把内存打满——备份按流式写盘，台账逐条写入。
- 时间跳变（系统时钟回拨）：保留期判断以单调的生成顺序为准，避免删掉「最新」的那份。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 任何档案记录被永久删除时，系统 MUST 在删除前把该记录的完整内容（含 `file` 路径、标签、阅读进度、判定为删除的时间）写入一份可查询的删除台账。
- **FR-002**: 台账 MUST 有保留期（默认 30 天，可配置），到期由既有的周期性清理任务清除。
- **FR-003**: 用户 MUST 能列出台账条目（含标题、删除时间、原文件路径），并对单条或全部执行恢复。
- **FR-004**: 恢复 MUST 重建记录本身及其元数据；文件仍在磁盘上的，恢复后立即可用；文件缺失的，记录以「文件缺失」状态存在而不是被丢弃。
- **FR-005**: 恢复时若同 id 记录已存在，系统 MUST 跳过该条并在结果里报告，不得覆盖。
- **FR-006**: 台账写入失败时，删除 MUST 继续，但结果 MUST 明确标注该次删除不可撤销。
- **FR-007**: 系统 MUST 按可配置的 crontab 计划自动生成完整备份（快照）：`snapshot_cron` 是 6–7 段 cron 表达式（`秒 分 时 日 月 星期 [年]`，按服务器本地时区求值，默认 `0 0 3 * * 1` 即每周一 03:00:00），计划可由用户关闭。同一命中不得重复生成（含重启后），停机错过的命中在下次启动后只补一次，改计划后无需重启即生效；非法表达式必须被拒绝并指出是哪一段。
- **FR-008**: 系统 MUST 在所有破坏性批量操作（清理数据库、导入恢复、索引重建、台账到期清除）之前生成一份「操作前」备份。
- **FR-009**: 自动备份 MUST 与手动导出的备份同格式，且能通过现有的恢复入口直接使用。
- **FR-010**: 自动备份 MUST 按 7 份每日 + 4 份每周的保留策略清理，且不得删除最近一份可用的备份。
- **FR-011**: 用户 MUST 能在设置页看到自动备份列表、下载其中任意一份、并用它发起恢复。
- **FR-012**: 一次操作计划删除的记录数超过阈值（默认：超过记录总数 25% 且不少于 50 条，可配置）时，系统 MUST 拒绝执行并要求显式确认；未确认时不得删除任何记录。
- **FR-013**: 已确认的批量删除 MUST 在任务结果与审计日志里记录「已确认」以及删除数量。
- **FR-014**: 扫描与清理 MUST 在日志和任务结果中输出：扫描到的文件数、数据库记录数、两者重合比例、库目录来源（拿不到时标注未知）。
- **FR-015**: 上述诊断信息 MUST 在任何运行环境下都能输出到可用字段，不得因为拿不到挂载信息而使扫描或清理失败。
- **FR-016**: 所有新增的破坏性接口 MUST 遵循既有的权限模型（会话管理员），并写入审计日志。

### Key Entities

- **删除台账条目（Deletion journal entry）**：一条被删除档案的完整快照 + 删除时间 + 删除来源（清理 / 单条删除 / 内部清理）。
- **自动备份（Snapshot）**：一份完整备份文件 + 生成时间 + 生成原因（每日 / 操作前）+ 是否可用。
- **删除守卫阈值（Deletion guard threshold）**：允许单次操作删除的比例与绝对量下限，可配置。
- **库目录诊断（Library diagnostics）**：扫描文件数、记录数、重合比例、库目录来源。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在一次「删除了 100 条记录」的误操作之后，运维能在 2 分钟内把这 100 条记录全部恢复到操作前的状态（含标签与阅读进度）。
- **SC-002**: 一个从不手动备份的实例，在任意一天都能找到最近 24 小时内的完整备份。
- **SC-003**: 一次会删除超过阈值比例的操作，在不确认的情况下删除 0 条记录。
- **SC-004**: 面对错误的库目录，运维能在扫描结束后 1 分钟内从日志判断出「库目录不对」，无需人工比对文件数。
- **SC-005**: 上述能力在容器与原生安装、Linux/macOS/FreeBSD 上均可使用；平台缺失的诊断字段以「未知」呈现而不是报错。

## Assumptions

- 复用既有的备份文档构建器与恢复入口；本特性不改变备份格式，只增加「谁、什么时候、为什么」生成，以及保留策略。
- 复用既有的周期性清理任务框架来驱动台账到期清理与备份保留策略，不新增独立调度器。
- 台账存储与备份文件都放在已经持久化的数据目录下（备份在 `<data>/backups/`，与 database/thumb 平级），容器部署无需新增挂载。
- 台账只覆盖「记录删除」，文件删除仍由既有回收站负责；两者互补，不合并语义。
- 恢复以记录为单位；不尝试还原被删除档案的缩略图缓存（可按需重建）。
- 阈值与保留期都以设置项形式暴露，默认值：台账 30 天、备份 7 日 + 4 周、删除守卫 25% 且 ≥50 条。
- 设置页只增加「备份列表 / 台账列表」两块最小可用界面；更复杂的运维界面不在本特性范围内。
- 单次操作删除的记录数上限与既有批量接口的分页/超时约束一致，不引入新的长事务语义。
