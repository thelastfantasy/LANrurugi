# Feature Specification: 入库完整性（下载 → 暂存 → 书库）

**Feature Branch**: `feat/share-bind-interface`（沿用当前分支，与 020–026 一致）

**Created**: 2026-11-13

**Status**: Draft

**Input**: 用户提问：「使用下载插件下载文件时，从 temp 目录移动到漫画目录的步骤，有块校验重试或移动后整文件校验的机制吗？没有的话有必要加吗？」随后讨论了 BLAKE3、`blit-core`、复制时用单独队列做流水线回读校验，并要求把讨论中发现的所有环节（包括续传、打包、各条入库路径、落盘顺序）都记进 spec 和 plan。

## Context

一个文件从下载到成为书库档案要经过：网络 → `.part` 部分文件 →（续传时追加）→（多资源时本地打包成 zip）→ 暂存区文件 →（跨文件系统时复制）→ 书库内的 `.ingest-*` 临时名 → 改名进 `<桶>/<id>.<ext>` → 写档案记录。

目前整条链上只有两处完整性检查：下载阶段对照 `Content-Length` 判截断（`crates/lanrurugi-api/src/download_manager/stream.rs:116` 的 `Truncated`），以及续传时用 `If-Range` 确认服务端内容没变（`stream.rs:247`）。档案 id 是「前 512000 字节 + 文件大小」的 SHA-1（`crates/lanrurugi-storage/src/id.rs:71` `size_aware_id`），不覆盖 512KB 之后的内容。

### 现状与缺陷证据（Investigation Record）

调查对象：`feat/share-bind-interface` @ `516e9c8`。

| # | 缺陷 | 证据 | 后果 |
|---|---|---|---|
| G1 | **复制少了也算成功，随后删源文件** | `crates/lanrurugi-core/src/io.rs:60-82` `copy_file`：`read` 返回 0 就 `break`，不比较 `copied` 与开头取得的 `len`；`move_file`（`:53-57`）随即 `remove_file(from)`；调用方 `download_manager/mod.rs:316` `rename_or_copy` 丢弃返回值 | 得到截断的书库文件，源文件已删。接管已有文件（`ingest.rs:313`，`keep_bytes_on_failure`）时源文件是用户唯一的一份 |
| G2 | **不落盘就删源文件** | `copy_file` 只 `flush()`，全仓下载/入库路径无 `sync_all`/`sync_data`（`stream.rs` 中为零） | 断电后目标未落盘而源已删；书库在 NFS/SMB 上时，ENOSPC/EIO 常在 fsync 或 close 时才报告，tokio 在 drop 时吞掉 close 错误 |
| G3 | **改名前后不保证落盘顺序** | 同文件系统路径直接 `rename`（`mod.rs:320`、`ingest.rs:365/390`、`stream.rs:706`），被改名的文件从未 fsync，目录也不 fsync | 非 ZFS（如 ext4 延迟分配）上可能出现「改名已落盘、数据未落盘」的零长度/空洞文件 |
| G4 | **续传信任 `.part` 当前长度** | `stream.rs:345-359` 以 `metadata(part_path).len()` 作为 `existing_len`，`:405` 发 `Range: bytes=<len>-`；写入过程中从不 fsync | 进程或机器在下载中途崩溃后，`.part` 尾部可能是零或残缺数据；续传按长度拼接，总长等于 `Content-Length`，长度检查通过，文件内容却是坏的 |
| G5 | **没有全文件指纹** | 档案记录只有 `size_aware_id`；共享导入单独对整文件算 BLAKE3（`share_net/import.rs:678`） | 512KB 之后的静默损坏无法发现；共享时要重算；无法做书库巡检 |
| G6 | **出错后的恢复不完整** | `put_bytes_back`（`ingest.rs:772`）只在部分失败分支调用 | 某些失败路径下暂存文件既不在原处也不在书库 |

已核对并排除：`tempmaxsize` 的自动清理（`ingest.rs:581-655`）只裁剪缩略图缩放缓存，不碰下载暂存区，不会在复制中途删除或截断暂存文件。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 移动档案时绝不丢失唯一的一份（Priority: P1）

管理员通过下载插件、上传或启动时接管把档案放进书库。无论暂存区与书库是否在同一文件系统、中途是否出错或断电，档案要么完整地出现在书库里，要么原文件仍在原处可重试——不会出现「书库里是残缺文件，原文件已经被删」。

**Why this priority**: 这是唯一会造成不可恢复数据丢失的缺陷（G1/G2/G3），而接管路径处理的是用户唯一的副本。

**Independent Test**: 构造一个复制过程中源文件被截短的场景、一个写入报错的场景、一个「复制完成后、删源前」中断的场景，确认三者都不会删除源文件，且书库中不留下被当作完整档案的残缺文件。

**Acceptance Scenarios**:

1. **Given** 暂存区与书库在不同文件系统，**When** 复制期间源文件被截短，**Then** 本次入库失败、源文件保留在原处、书库内不产生档案记录，队列行显示可重试的错误。
2. **Given** 书库所在文件系统写满，**When** 复制一个大档案，**Then** 入库失败并给出「空间不足」类错误，源文件保留。
3. **Given** 一次入库已完成复制但尚未删除源文件，**When** 进程被杀并重启，**Then** 重启后不会把未落盘的目标当作完整档案，源文件仍可用于再次入库。
4. **Given** 暂存区与书库在同一文件系统，**When** 改名完成后立即断电，**Then** 重启后该档案要么完整存在、要么仍在暂存区，不会是零长度文件。

---

### User Story 2 - 中断后续传不会拼出坏文件（Priority: P1）

下载中途进程崩溃或机器断电后，重新开始的下载只从「确认已经安全写下」的位置续传，不会把崩溃时残留在部分文件尾部的垃圾数据当作已下载内容。

**Why this priority**: G4 产生的坏文件长度完全正确，现有的所有检查都会放行，而且一旦入库就会被当作正常档案长期保存。

**Independent Test**: 下载到一半时模拟崩溃，并人为把部分文件尾部改成零，再触发续传；确认续传从最后一个确认点开始，最终文件与一次性完整下载的结果逐字节相同。

**Acceptance Scenarios**:

1. **Given** 一个下载在 60% 处因进程崩溃中断、部分文件尾部有未确认数据，**When** 重新开始该下载，**Then** 系统丢弃未确认部分、从最后确认位置续传，最终文件与原始资源一致。
2. **Given** 没有任何确认记录的旧版部分文件（升级前遗留），**When** 重新开始下载，**Then** 系统不信任其内容，按「从头下载」处理。
3. **Given** 服务端不支持续传，**When** 下载中断后重试，**Then** 行为与现在一致（从头下载），不因本功能报错。

---

### User Story 3 - 每个新档案都有可核对的全文件指纹（Priority: P2）

新入库的档案在记录里带有一份覆盖整个文件的指纹，这份指纹在字节第一次被系统经手时（下载写入、本地打包、接收上传、接手插件产物或已有文件）就计算出来，并随下载队列行一起持久化；之后跨文件系统复制时，对实际复制的字节再算一次并与之比对，不一致就判定暂存文件已损坏。

**Why this priority**: 补上 512KB 之后无法发现的静默损坏（G5），并为共享、重复检测和以后的书库巡检提供同一份事实；它不阻止丢数据，所以排在 P1 之后。

**Independent Test**: 下载一个档案，读出记录中的指纹并与独立计算的结果比对；再构造一个「暂存文件在入库前被改动一个字节」的场景，确认入库被拒绝且队列行提示重新下载。

**Acceptance Scenarios**:

1. **Given** 一次正常下载，**When** 档案入库完成，**Then** 档案记录带有全文件指纹，且与对书库文件重新计算的结果一致。
2. **Given** 下载完成后、入库前暂存文件中间某字节被改动，**When** 入库，**Then** 入库失败、源文件保留、队列行标记为需要重新下载。
3. **Given** 下载完成后服务重启，**When** 之后再入库，**Then** 比对使用的是下载时记录的指纹，而不是重启后对暂存文件现算的值。
4. **Given** 共享导入的档案，**When** 入库，**Then** 直接沿用传输层已校验的指纹，不重复对整个文件计算。
5. **Given** 多资源打包、插件自行下载、网页上传、启动时接管这几条路径，**When** 入库，**Then** 各自在第一次经手字节时得到指纹，记录里都有指纹。

---

### User Story 4 - 可选的「严格校验」：确认写到书库的数据就是复制的数据（Priority: P3）

书库挂在网络存储（NFS/SMB）上的管理员，可以在设置里打开严格校验：复制过程中由单独的任务把刚写下的块绕过本机缓存读回并比对，不一致则本次入库失败。默认关闭。

**Why this priority**: 只在网络挂载的书库上有实际价值；在本地 ZFS（维护者自己的部署）上，回读要么只读到缓存、验证不到磁盘，要么在 HDD 上拖慢写入。

**Independent Test**: 在支持绕过缓存读取的文件系统上打开开关，入库一个大档案，确认回读确实发生、结果一致时入库成功；用测试替身让回读返回不同数据，确认入库失败且源文件保留；记录开关前后的耗时。

**Acceptance Scenarios**:

1. **Given** 严格校验关闭（默认），**When** 入库，**Then** 不发生任何回读。
2. **Given** 严格校验打开，**When** 回读的某块与复制的数据不一致，**Then** 入库失败、源文件保留、错误指出不一致的偏移范围。
3. **Given** 严格校验打开但当前平台/文件系统无法绕过缓存读取，**When** 入库，**Then** 系统记录一次说明「回读无法验证磁盘，已跳过」的日志，不假装校验通过。

---

### User Story 5 - 档案字节被改写后指纹随之更新（Priority: P3）

分卷拆分、补页、覆盖式重复处理等会改写书库文件的操作，完成后档案记录里的指纹同步更新；旧书库里没有指纹的档案可以通过一个手动触发的后台任务补算。

**Why this priority**: 不做这一步，指纹会过期，以后任何基于指纹的巡检都会误报。

**Independent Test**: 对一个有指纹的档案执行补页，确认记录中的指纹变化且与新文件一致；对一个无指纹档案运行补算任务，确认得到指纹。

**Acceptance Scenarios**:

1. **Given** 一个有指纹的档案，**When** 执行会改写文件字节的操作，**Then** 操作完成后指纹与新文件一致。
2. **Given** 书库中有无指纹的档案，**When** 管理员手动运行补算任务，**Then** 任务以有限的资源占用逐个补齐，可在任务控制台看到进度，可取消。

### Edge Cases

- 源文件在复制过程中被其他进程追加或替换（长度变长）：以开始复制时的长度为准，复制后长度或指纹不一致即失败。
- 书库与暂存区在同一文件系统但跨 bind mount（`rename` 返回 EXDEV）：按跨文件系统处理，走复制路径的全部检查。
- 断电发生在「目标已落盘、源未删除」之间：重启后同一内容会再次入库，按现有「同 id 已存在」逻辑处理，不产生重复档案。
- 磁盘写缓存不服从 fsync（部分消费级硬盘、macOS 默认 fsync）：macOS 使用完整刷盘调用；无法保证的平台在文档中说明。
- 指纹比对失败时暂存文件本身就是坏的：不再从它重试复制，直接要求重新下载；接管路径（用户唯一副本）则保留文件并报告，不删除、不重下载。
- 续传确认点比服务端 `If-Range` 判断更旧：以较旧者为准（只从确认点续传）。
- 计算指纹失败（读取错误）：视同入库失败，不写入没有指纹的「新」档案记录，也不删除源。
- 严格校验开启时内存占用：同时进行的复制数 × 队列深度 × 块大小有上限。

## Requirements *(mandatory)*

### Functional Requirements

**移动与落盘（US1）**

- **FR-001**: 跨文件系统复制 MUST 在结束时核对已复制字节数等于开始时源文件的长度，并核对目标文件长度等于该值；任一不等 MUST 视为失败。
- **FR-002**: 系统 MUST 仅在目标文件内容与其所在目录都已持久化之后才删除源文件；持久化失败 MUST 视为复制失败。
- **FR-003**: 同文件系统改名入库 MUST 先持久化被改名文件的内容，改名后持久化目标目录。
- **FR-004**: 任何入库失败 MUST 让源字节回到可重试的位置（原暂存位置，或接管路径下的原位置），且书库中不留下被记录为档案的残缺文件；遗留的 `.ingest-*` 临时文件由现有清扫逻辑回收。
- **FR-005**: 上述保证 MUST 同样适用于 `_byname` 搬家和其他复用同一复制实现的路径。

**续传（US2）**

- **FR-006**: 可续传下载 MUST 周期性持久化部分文件并记录「已确认落盘的字节位置」，记录与现有续传元数据存放在一起。
- **FR-007**: 续传 MUST 先把部分文件截断到最后确认位置，再从该位置请求剩余字节；没有确认位置的部分文件 MUST 从头下载。
- **FR-008**: 确认的频率 MUST 有上限（按字节量或时间），使持久化开销对下载吞吐的影响可忽略。

**全文件指纹（US3）**

- **FR-009**: 系统 MUST 为每个新入库档案计算覆盖整个文件的 BLAKE3 指纹，并作为档案记录的新增字段保存；档案 id 的算法与已有 id MUST 保持不变。
- **FR-010**: 指纹 MUST 在字节第一次被系统经手时计算，且不为此额外读一遍文件：托管下载在写入时增量计算（续传时从确认点之前的已确认数据恢复）、本地打包对输出流计算、上传对接收的数据计算；插件自行下载、启动接管、监视器发现的文件在系统接手时读一遍计算；共享导入沿用传输层已校验的指纹。
- **FR-011**: 入库前的指纹 MUST 随下载队列行持久化，使服务重启后仍以原始指纹为比对基准。
- **FR-012**: 跨文件系统复制 MUST 对实际复制的字节计算指纹并与基准比对；不一致 MUST 判定暂存文件已损坏：下载来源的队列行进入「需要重新下载」，接管来源保留文件并报告错误，均不删除源。
- **FR-013**: 同文件系统改名入库 MUST 直接沿用基准指纹，不为校验而额外读文件。

**严格校验（US4）**

- **FR-014**: 系统 MUST 提供默认关闭的「严格校验」设置；开启时，复制过程中由独立任务把已写入的块绕过本机缓存读回并与复制的数据比对，不阻塞后续块的复制。
- **FR-015**: 严格校验的待校验块数 MUST 有上限，超过时复制等待，保证内存占用有界。
- **FR-016**: 当前平台或文件系统无法绕过缓存读取时，系统 MUST 跳过回读并记录原因，MUST NOT 把读缓存的结果当作校验通过。

**指纹维护（US5）**

- **FR-017**: 任何改写书库档案字节的操作 MUST 在完成后更新该档案的指纹。
- **FR-018**: 系统 MUST 提供手动触发的后台任务，为没有指纹的档案补算指纹；任务 MUST 遵守项目对后台任务的资源上限与负载退避，可在任务控制台查看与取消。

**可观测性**

- **FR-019**: 长度不符、持久化失败、指纹不符、回读不符 MUST 各自有可区分的错误类型，出现在队列行与日志中，且包含路径与字节位置等定位信息。

### Key Entities

- **全文件指纹**：整个档案文件内容的 BLAKE3 摘要。属于档案记录的新增可选字段；旧档案没有，补算后才有。
- **入库基准指纹**：入库前随下载队列行保存的指纹，入库成功后写入档案记录；入库失败时保留在队列行上供重试使用。
- **续传确认点**：一个可续传下载已持久化的字节位置（以及恢复增量指纹所需的状态），与现有续传元数据（URL、ETag、Last-Modified、文件名）同处保存。
- **严格校验设置**：全局开关，默认关闭。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在故障注入测试中（复制中源被截短、写入报错、删源前中断、改名后断电），源文件被删除而书库中只有残缺文件的情况出现 0 次。
- **SC-002**: 在「下载中途崩溃并破坏部分文件尾部」的测试中，续传后的文件与完整资源逐字节一致的比例为 100%。
- **SC-003**: 默认配置下，一个 1.4 GB 档案的入库总耗时增加不超过 5%（相对本功能前，同一硬件上实测）。
- **SC-004**: 本功能上线后新入库的档案 100% 带有全文件指纹，且抽样复算全部一致。
- **SC-005**: 在暂存文件被改动一个字节的测试中，入库被拒绝的比例为 100%。
- **SC-006**: 严格校验开启时，在维护者的 NAS（HDD 池）上测得的入库耗时增幅有记录；超过 30% 时在设置说明里写明。

## Assumptions

- 维护者自己的部署是 LANrurugi 跑在 TrueNAS 本机、书库为本地 ZFS（HDD 池 `tank`），暂存区在容器自己的文件系统中（见 `~/.dsh/notes/lanrurugi-ops.md`）；写入后的磁盘完整性由 ZFS 校验和负责，本功能不重复做磁盘巡检。
- 网络段（服务端 → 本机）没有可核对的参照：HTTPS 负责传输中不被篡改，`Content-Length` 负责截断；来源站提供哈希时的核对不在本功能范围内（见 Out of Scope）。
- BLAKE3 已是工作区依赖（`Cargo.toml` `blake3 = "1.8.7"`），宪法原则 III 也要求新的哈希工作优先使用 BLAKE3。
- 不引入 `blit-core`：评估结论是 0.1.2 单版本、约 5.5 万行、依赖 gRPC/mDNS 等与本需求无关的组件，且其复制实现不做复制后校验（评估记录见 research.md）。
- 块级「校验失败只重传该块」不做：本地与 NAS 文件系统的写错误不是偶发的，失败应让整次移动失败并保留源。

## Out of Scope

- 来源站提供哈希时的下载内容核对（插件契约需要新增字段，单独立项）。
- 定期书库巡检（基于指纹发现位腐烂）——本功能只保证指纹存在且正确，巡检另立 spec。
- 对已有档案 id 算法的任何改动。
