# LANrurugi

[LANraragi](https://github.com/Difegue/LANraragi)（セルフホスト型の漫画・同人誌ライブラリ管理ソフト）をゼロから
Rust + React で書き直したプロジェクト。既存の LANraragi インストールとの機能的同等性、および
データ/API の完全な互換性を目指しつつ、既知の重複検出の不具合を修正し、レガシーの Perl 実装には
存在しなかった真のマルチコア並行処理を追加している。

**ステータス**: Phase 1（`specs/001-lanrurugi-full-rewrite/`）は実装済み — 8 つのユーザーストーリー
（ライブラリの継続性、非マージ型の取り込み、サードパーティ API 互換性、プラグインによるメタデータ
拡充、バックアップ/エクスポート、重複修復、UI ローカライズ、レガシーシステムとの並行処理ベンチマーク）
はすべて完了している。詳細は `specs/001-lanrurugi-full-rewrite/tasks.md` を参照。Phase 1 に対する
追加機能（addendum）3 件も完全に実装済み: `specs/002-job-console/`（バックグラウンドジョブ管理 UI）、
`specs/003-ui-test-automation/`（Vitest + Playwright によるフロントエンドテストカバレッジ）、
`specs/005-download-plugin-progress/`（実際のバイト単位のダウンロード進捗、ドメイン単位の並行数/
レート制限）。Phase 2（`specs/004-ocr-manga-translation/`、ページ内漫画翻訳）のみ、計画段階で実装は
まだ行われていない。これは constitution の Principle VI に従い、Phase 1 をブロックすることも
Phase 1 にブロックされることもないよう意図的に独立させているためである。

## スタック

- **バックエンド**: Rust（Tokio 非同期ランタイム、Axum Web フレームワーク、CPU バウンドな並列処理には
  Rayon）。`crates/` 配下の単一の Cargo ワークスペースが、`serve` / `rebuild-index` / `bench`
  サブコマンドを持つ単一バイナリ `lanrurugi-server` を生成する。
- **データストア**: Redis。レガシーのデプロイ環境からそのまま流用（論理 DB 5 個 — 詳細は
  `crates/lanrurugi-storage/src/redis.rs` を参照）。
- **フロントエンド**: React 19 + TypeScript + Vite + Tailwind + Zustand + TanStack Query。
  `apps/frontend/` 配下。
- **プラグイン**: サンドボックス化された Deno サブプロセス。プラグインの名前空間ごとに 1 プロセス
  （`crates/lanrurugi-plugin/`）。
- **ベンチマークハーネス**: `crates/lanrurugi-bench/` — 合成ライブラリ生成器、`criterion` による
  マイクロベンチマーク、そしてこのバイナリと実際のレガシー LANraragi インスタンスを並行して
  同時駆動するクロスシステム比較ハーネス。

## LANraragi からの改善点

これは単に「同じ機能を別の言語で書き直しただけ」ではない。以下は機能面/アーキテクチャ面での改善点の
具体的な一覧であり、それぞれがレガシーに実在する既知の不具合を修正しているか、レガシーには一度も
存在しなかった機能を追加しているものである — 「Rust を使ったから自動的に良くなった」という主張では
ない。**parity（同等性）** と明記されているセクションは意図的な互換性維持の判断であり、このリストが
過大な主張をしないようにするために明示している。

### データ整合性と重複検出

- **レガシーの誤った重複統合の不具合に対する本当の修正。** レガシーはアーカイブの ID を、ファイル先頭
  512,000 バイトのみの `SHA-1`（`~/LANraragi/lib/LANraragi/Utils/Database.pm::compute_id`）として
  計算している — たまたま先頭の内容が一致する（例: 表紙ページが同一で、それ以降のページが異なる）
  2 つの異なるファイルは同一ハッシュ値となり、静かに 1 つのライブラリエントリに統合されてしまい、
  どちらか一方のメタデータが上書きされて失われる。LANrurugi のデフォルト ID アルゴリズム
  （`crates/lanrurugi-storage/src/id.rs::size_aware_id`）は、実際のファイルサイズをハッシュ入力に
  組み込むことで、先頭部分は共通していても長さが異なる 2 つのアーカイブがもはや衝突しないようにして
  いる — その一方で、元のレガシー ID も引き続き計算され、既存ライブラリとの読み取り互換性のために
  永続的に保持される（constitution Principle I）。SHA-1 は（BLAKE3 のような新しいハッシュに切り替える
  のではなく）意図的にそのまま維持されている。これは、レガシーコードの他の箇所がアーカイブ ID を
  固定 40 桁 16 進文字の Redis キーの glob パターンで列挙しているためであり、ダイジェスト長を変更すると
  それらすべての glob パターンが静かに壊れてしまうからである。
- **その不具合によってすでに損傷したライブラリのための一回限りの修復ツール**（`lanrurugi
  rebuild-index` / `POST /database/rebuild-index`、User Story 6） — すべてのアーカイブの ID を
  新しいアルゴリズムで再計算し、過去の誤った統合によって隠されていたファイルは、正しく追跡されていた
  方のタグ/読書進捗を乱すことなく、独立したタグ付け可能なアーカイブとして再び現れる。レガシーには
  相当する修復メカニズムが一切存在しない — 一度 2 つのアーカイブが統合されると、統合されたままだった。
- **ファイル名の衝突とコンテンツの衝突はもはや同じ扱いをされない。** `QueueError` は
  `DuplicateReasonKind`（`ContentHash` 対 `Filename`）を保持しており、この本質的に異なる 2 つの状況が
  本当に異なる処理を受けられるようにしている: 実際のコンテンツ重複は無条件に拒否され（「上書き」による
  回避はない — 同一コンテンツの上書きは以前は無駄な作業であるだけでなく、元の `date_added` も失われて
  いた）、一方で*異なる*コンテンツによるファイル名の衝突では、ダウンロードされたバイト列が一時ファイルに
  ステージングされ、2 つの新しいエンドポイント — `POST /download_queue/{id}/overwrite` と
  `POST /download_queue/{id}/rename` — を通じて本当の選択肢が提示される。これにより新しいダウンロードは
  既存のアーカイブを置き換えるか、新しい名前で独立して共存するアーカイブとしてカタログ化されるかを
  選べる。レガシーには相当する機能がない。この種の衝突は以前は検出されないか、静かに上書きされる
  かのどちらかだった。1 時間ごとのバックグラウンドスイープが、24 時間以上未解決のまま放置された
  ステージング済みファイルを回収し、キューアイテムを「期限切れ、再ダウンロードしてください」という
  明確な状態に降格させる。もはや存在しないバイト列に対して操作を提示し続けることはない。

### 並行処理とアーキテクチャ

- **3 プロセスではなく統合された 1 プロセス。** レガシーはメインの Mojolicious アプリ、別プロセスの
  ファイル監視ワーカー `Shinobu`、別プロセスのジョブキューワーカー Minion という、3 つの独立した
  OS プロセスを実行する。LANrurugi は `clap` ベースの単一バイナリ（`lanrurugi-server`）であり、
  `serve`/`rebuild-index`/`bench` のサブコマンドを持つ。`serve` は HTTP API、`notify` ベースの
  ファイル監視、Deno プラグインプールをすべて別プロセスとしてではなく、1 つの Tokio ランタイム内の
  タスクとして実行する。
- **ファイルを静かに破損させかねない同時ダウンロードの競合状態に対する本当の修正。** かつての
  ファイル名衝突検出は、「チェック済み、衝突なし」と「ファイルを書き込んだ」の間にロックのない
  一度限りのディレクトリスキャンだった — 同じ解決済みファイル名に対して競合する 2 つのダウンロードが
  両方ともチェックを通過してしまい、一方がディスク上でもう一方のバイト列を静かに上書きする一方で、
  両方のカタログレコードが同じ（今や半分間違った）ファイルを指したままになりうる。ファイル名単位の
  非同期ロック（`AppState::lock_filename`、`crates/lanrurugi-api/src/state.rs`）で、チェックから
  書き込みまでのウィンドウ全体にわたってロックを保持することで修正された。RAII ガードにより、
  早期リターンのエラーパスを経由しても確実に解放される。
- **強制的なプロセスレベルの中断ではなく、協調的なダウンロードキャンセル。** キューアイテムごとの
  `CancellationToken` により、ダウンロードループはネットワークエラーをチェックするのと同じ箇所で
  停止要求に気づくことができ、`AbortHandle` 方式のハードキルのように `write_all()` の途中でドロップして
  クリーンアップの機会がないまま、追跡不能な孤児一時ファイルを残す代わりに、既存の部分ファイル
  クリーンアップ経路をそのまま再利用する。レガシーにはダウンロード単位の停止メカニズムが一切存在
  しない。
- **明示的で正しい CPU/非同期のブリッジング。** CPU バウンドな作業（ハッシュ計算、画像のデコード/
  リサイズ）はすべて `rayon` 経由で実行され、`tokio::task::spawn_blocking` を通じて非同期ランタイムに
  ブリッジされる — 意図的に非同期ワーカースレッド上でインラインに実行することは決してなく、
  一括スキャン/再インデックスが HTTP サーバーが同時に処理しているリクエストを止めてしまうことがない。
  レガシーのリクエストごとにシングルスレッドという Perl モデルには「リアクタをブロックしない」という
  概念自体が存在せず、正しく扱うも間違って扱うもない。これは以下のベンチマークスイートが計測する
  まさにその一括処理（フルライブラリスキャン、重複修復のための再インデックス）のための、新しい
  本物のマルチコア並列処理である。
- **高コストで頻繁に繰り返される処理のリクエスト集約。** 同じ欠落サムネイル、あるいは同じアーカイブ
  ページに対する同時リクエストは、それぞれが独立してアーカイブファイルを最初からスキャンし直すのでは
  なく、1 回の再生成/読み取りに集約される — レガシーのリクエストごとのモデルでは避けることが
  できなかった（あるいは避けようがなかった）種類の重複作業である。

### ダウンロードパイプライン

- **実際のバイト単位のダウンロード進捗。** 以前は、ダウンロードプラグインの実際の HTTP 転送は
  Deno でサンドボックス化されたプラグインプロセスの内部で見えないまま行われており、ホスト側が
  進捗を観測する方法が一切なかった。実際の転送は Rust 側（ストリーミング `reqwest`）に移動したため、
  `downloaded_bytes`/`total_bytes` は本物の値となり、キューアイテムが 0% から 100% へいきなり
  飛ぶのではなく、本物の進捗バーへとストリームされる。
- **ドメインごとの並行数制限とレート制限。** プラグインごとに設定可能（完全一致ホスト名およびワイルドカード
  ドメインのルール、トークンバケット方式のレート制限）で、設定 UI からユーザーが上書きできる —
  レガシーのダウンロードプラグインにはこれを表現/強制する方法が一切なかった。
- **非 ASCII ダウンロードファイル名に対する、実際に検証済みのバグ修正。** 一部の実際のダウンロード
  サーバーは、正当な UTF-8 ファイル名を単純な `Content-Disposition: filename="..."` ヘッダーに
  直接送ってくる（厳密には RFC 6266 準拠ではないが、実際にはよくある）— もとのファイル名解析コードは
  `HeaderValue::to_str()` を使用しており、これは非 ASCII バイトがあると静かに失敗するため、これらの
  ダウンロードは意味のないギャラリー ID の文字列を保存ファイル名として使うフォールバックに陥っていた。
  ヘッダーの生バイト列を読み取り、まず UTF-8 としてデコードを試み、本当に UTF-8 でないサーバーに
  対してのみ（決して失敗しえない）Latin-1 バイトマッピングにフォールバックすることで修正された。
- **ダウンロードのキャンセルは、単なるフロントエンドの見せかけではなく、実際に永続化された状態である。**
  実際のキューアイテムのステートマシンに `Cancelled` 状態が追加された（ページの再読み込みを
  またいで維持され、`Queued`/`Error` とは区別され、独自の「已取消/Cancelled」という UI 表示を持つ）。
  これは、以前のフロントエンドのみの楽観的状態更新の実装がリロードで消えてしまうことが判明した
  後に追加されたものである。
- **同一 URL への重複した進行中のダウンロードは、検出なしに黙って同時実行を許すのではなく、
  現在は拒否される（`409`）。** また、実行中のダウンロードのキューレコードはもはやその下から
  削除できない（以前はバックグラウンドタスクが静かに孤立してしまい、その後観測したり停止したり
  する方法がなかった）。

### エラー処理と国際化

- **すべてのダウンロードキューのエラーが、生の文字列ではなく、構造化され翻訳可能なものになった。**
  `QueueError`（`crates/lanrurugi-core/src/queue_error.rs`）は、自由記述テキストフィールドを一切
  持たない、構造化された補間可能なデータのみのクローズドな enum である。各バリアントは安定した
  数値コード（該当する場合は 409/422 のような実際の HTTP 相当コード、HTTP に相当するものがない
  純粋なビジネスエラーには 1000 以上のコード）を持ち、フロントエンドは各 `kind` を実際に翻訳された
  文字列としてレンダリングする — 重複アーカイブエラーの `existing_id` を、既存アーカイブへの実際に
  クリック可能なリンクに変換することも含まれ、これはレガシーの単純なエラーテキストには一切なかった
  ものである。
- **プラグイン SDK も同じ構造化エラー処理の恩恵を受けた。** プラグイン側のあらゆる
  `throw new Error("...")`/`{error: "a string"}`（出荷済みプラグイン群全体でおよそ 40 箇所の
  呼び出し）が `{error_code, data}` の形に変換された。ここで `error_code` は、そうでなければ
  英語を読めないユーザーが立ち往生してしまう不透明な英語テキストではなく、i18n の参照キーを
  兼ねている。

### プラグインのサンドボックス化

- **プラグインごとの最小権限 — レガシーにはプラグインの権限モデルが一切存在しない。** 各プラグインの
  名前空間は独自の Deno サブプロセスを持ち、そのプラグイン自身が宣言する厳密な
  ネットワーク/読み取り/書き込み権限のみで起動される（本物のワーカーが起動される前に、使い捨ての
  ゼロ権限起動プローブによって照会される） — 他のすべてのプラグインの権限の和集合を与えてしまう
  共有プロセスでは決してない。
- **プラグイン名前空間パラメータに対する実効的なパストラバーサル対策。** これは認証なしの HTTP
  クエリ文字列（`POST /plugins/use?plugin=...`）から渡されるものであり、`..` によるトラバーサルと
  絶対パスを拒否し、専用のテストでカバーされている。
- **1 つのプラグインの失敗が他のプラグインを道連れにしない。** クラッシュしたり、タイムアウトした
  プラグイン呼び出しは、そのプラグイン自身のワーカーのみを落とす（次回使用時に遅延的に再起動される）。
  他のすべてのプラグインのプールは影響を受けない。

### フロントエンド

- **一元化されたルート管理**（`apps/frontend/src/routes.ts`）が、以前は散在していた手書きのパス
  文字列を置き換えた — これは単なるリファクタリングではなく、実際のデッドリンクのバグを修正した:
  複数のページが、`BrowserRouter`（`HashRouter` ではない）を使用しているアプリの中で
  `#/reader/{id}` 形式のハッシュフラグメントを使用しており、これはブラウザのデフォルトナビゲーションを
  横取りする左クリックの `onClick` ハンドラーを通じてのみ「動作」していた — 中クリックでの新規タブ
  オープン、右クリックでのリンクコピー、アプリ自身の「リンクをコピー」ボタンは、これが一元化されて
  修正されるまで、すべて実質的に壊れていた。
- **本物の削除可能なチップを備えた、再構築されたタグエディター**（クリックで削除、Enter/カンマで
  確定、貼り付け時にカンマで分割、重複の拒否、オートコンプリート）が、退化した単なる `<textarea>`
  を置き換えた — その過程で、実際の挙動上のバグも修正された: メタデータプラグインの実行時に、
  未保存の編集内容が先に正しく保存されるようになった（レガシー自身の本来の保存してから取得する
  という順序と一致する）。これは以前の実装ではまったく行われていなかった。
- **検索フィルターの状態は、ブラウザの実際の戻る/進む履歴を、React Router 自身の `navigate()` を
  介して、正しく往復する。** `replaceState` のみの実装ではブラウザの戻るボタンでまったくナビゲート
  できなかったのに対し、今回はそれができる。
- **リーダー概要ページに追加された、全画面ズームプレビュー（ライトボックス）。** ページグリッドの
  各サムネイルにある虫眼鏡アイコンをクリックすると、大きなプレビュー + 現在ページの情報（ページ番号、
  ファイル名、解像度、サイズ、所属する章）+ 高速スクラブ可能でホバーすると自動的にプレビューが
  切り替わる横型フィルムストリップギャラリーが開く — いずれも、下にある概要モーダル自体の
  スクロール位置や実際の読書進捗には一切影響しない。レガシー自身のサムネイルグリッドは小さすぎて、
  内容だけで章の開始/終了ページを判断することができない。レガシーには同等の機能が一切存在しない。
- **章（目次）管理に関するいくつかの実際の改善。** 章の削除/編集は、アーカイブ内のすべての章を
  一覧表示して選択できるようになった — レガシー自身の実際の制限（`getCurrentChapter()`、移植漏れ
  ではない）である「リーダーが現在スクロールしている章」だけしか操作できないという制約はなくなった。
  よく使う章の種類（表紙/裏表紙/目次/カラーページ/おまけ/あとがき/イラスト + 第N章のドロップダウン）
  はワンクリックのプリセット、または数字キーのショートカット（0 = 目次、1〜9 = 対応する章）で
  設定できる。プリセットで設定された章タイトルは、内部で予約された識別子（`toc`/`c1`〜`c20`）として
  保存され、再設定時に重複排除される（「第4章」を再設定すると、古い重複エントリを残すのではなく、
  それを移動させる）。フロントエンドはこれらを実際のローカライズされた表示テキストに変換して表示する
  — これらのプリセットエントリは手動編集ダイアログでリネームすることはできず（重複排除の意味が壊れて
  しまうため）、削除してプリセットで再設定する必要がある。
- **`date_added` が、暦日単位の検索に対応した**（`date_added:2026-07-20`、設定ページで構成可能な
  サーバータイムゾーンに対して解決される）。これは、そのタイムゾーンにおけるその日の 00:00〜24:00
  までのタイムスタンプ範囲として解決される。レガシー自身の `date_added` は単なる Unix 秒数タグ
  であり、「日単位」で検索するという概念がまったく存在しない。タグの表示とその検索リンクも、
  同じタイムゾーンで一貫して `yyyy-mm-dd` として表示/解決されるようになった。
- **ライブラリのグリッドカードに追加された、「既読にする」/「未読にする」の右クリックメニュー
  項目。** 読書進捗を直接、最終ページまたは 0 に設定する — レガシーには、実際にアーカイブを
  ページ送りする以外に、既読状態を手動で切り替える方法が一切存在しない。
- **AI 支援による Tankoubon 編集。** メンバーアーカイブのタイトルからタイトル・章名・読む順序を
  提案する（DeepSeek 利用、複数候補、ワンクリック適用）。**AI 支援による Tankoubon 作成**も追加——
  まだどの Tankoubon にも属していないアーカイブを分析し、同一シリーズに属する可能性が高いグループを
  提案する（ローカル埋め込みモデルのみを使用、LLM キー不要）。

### 認証

- **固定 24 時間セッションに代わる、短命な JWT アクセストークン + ローテーション式リフレッシュ
  トークン。** ログイン状態は、本物の JWT（HS256）アクセストークン（短命）と、失効可能かつ単回使用
  のリフレッシュトークン（OAuth 2.1 スタイルのローテーション + 再利用検出——一度ローテーションされた
  リフレッシュトークンが再送されると、そのトークンファミリー全体が失効する）の組み合わせで管理される
  ようになった。フロントエンドは、アクセストークンが期限切れになった際に再ログインを強制することなく
  透過的に更新する。両方の有効期限は設定ページから変更可能。
- **レガシーの単一共有 `apikey` に代わる、ファーストパーティの API トークン管理システム。**
  レガシーの「インスタンス全体で固定の apikey 文字列を 1 つ共有する」という仕組みは、設定ページから
  作成・改名・失効させられる本物のマルチトークンシステムに置き換えられた。各トークンには Admin
  （トークン管理・アカウントセキュリティ・データベース削除を除く完全な権限）または Guest
  （読み取り専用）のロールと、任意の有効期限を設定でき、生の値は作成時に一度だけ表示される。これは
  意図的なリリース前の破壊的変更であり、レガシーの `Bearer base64(apikey)` / `?key=` 機構に依存する
  サードパーティクライアントは、変更なしに動作し続けることはもはや保証されない（下記の API
  互換性に関する注記を参照）。

### テスト基盤

- **Phase 1 が欠いたまま出荷した、2 層構成の自動テストスイート。** Vitest + React Testing Library
  は、バックエンド不要で高速なフック/ロジックの単体テストカバレッジを提供し、Playwright
  （Chromium + Firefox）は、実際に稼働するバックエンド + Redis に対する本物のエンドツーエンド
  カバレッジを、ワーカーごとに分離された Redis 環境で提供する。複数のテストスイートは、この
  プロジェクト自身の手動 QA によってすでに発見・修正された実際のバグを具体的にコード化しており、
  加えてスキャナーがサポートするすべてのアーカイブ形式にわたる体系的なフィクスチャカバレッジも
  備えている。
- **依存していたテスト基盤を実際に配線することで、死んだテストが発見・修正された。** あるコントラクト
  テストは、実際にはただスキップされているだけなのに静かに（`ok` として）通り続けていた。原因は、
  必要な Redis 接続文字列がコンテナ化されたテストランナーに一度も配線されていなかったためであり、
  これはこの修正が行われるまで、スイート内の Redis に依存するすべてのテストに当てはまっていた。
  この配線を修正したこと（単に問題の 1 つのテストを直しただけではなく）で、問題となっていたその
  テストが、すでに存在しないエンドポイント（対応する機能は別の仕組みに移行済みだった）に対して
  アサーションを行っていたことが即座に明らかになり、実際に相当する新しいテストに置き換えられた。

### ジョブコンソール

- バックアップ/リストア、サムネイル再生成、重複スキャン、インデックス再構築のために内部で
  すでに使用されているジョブレジストリを、実際に閲覧可能な管理ページとして表面化する —
  ライブの状態/進捗、ジョブごとの結果/エラーの検査、フィルタリング — これはレガシーでは Minion
  自身の管理 UI を通じてしか公開されていなかったものであり、レガシーを模倣する `/api/minion/*`
  API には手を付けない、別個の追加専用 `/api/jobs*` コントラクト上で提供される（Principle II）。

### 意図的に「改善」とは主張していないもの（設計上の同等性）

- SHA-1 は新しいハッシュにアップグレードされず、そのまま維持された — 詳細は上記のアーカイブ ID の
  セクションを参照。改善点はサイズを考慮した*入力*であり、ハッシュのプリミティブ自体ではない。
- RAR/7z アーカイブは、レガシー自身の実用的なアプローチに合わせて、引き続き `unrar`/`7z` を
  外部呼び出しすることで処理されており、ゼロから再実装されたわけではない。
- REST API コントラクトは、レガシー自身の OpenAPI 仕様から直接派生した、追加専用のものである —
  エンドポイントの形状/パス自体は影響を受けておらず、明確な目標は*API を再設計しないこと*である。
  **唯一、意図的な例外は認証機構そのものである**: レガシーの `Bearer base64(apikey)` / `?key=`
  方式は、リリース前に上記の JWT + API トークンシステムへ意図的に置き換えられた——これは「API
  コントラクトの互換性を維持する」という原則に対する唯一の意図的な逸脱である（対応する注記は
  `.specify/memory/constitution.md` の当該原則の末尾を参照）。
- 検索エンジンは、レガシーの Redis ベースのモデル（ソート済みセット、タグフィルタリング）をそのまま
  移植したものであり、新しい検索技術ではない — ここでは同等性そのものが実際の目標であり、この
  プロジェクトの目標スケールにおいて十分であると評価・確認されている。

## ビルドと実行

ツールチェーンのバージョンは `.mise.toml` に固定されている（`mise install` により、Rust、Node、
Deno、pnpm に加え、ビルド高速化のための `sccache`/`mold` を含めて、正確に再現される）。

```sh
# バックエンド
cargo build --release -p lanrurugi-server
./target/release/lanrurugi-server serve --redis-url redis://127.0.0.1:6379 \
  --library-path /path/to/existing/library

# フロントエンド（開発サーバー。上記バックエンドへ /api をプロキシする）
cd apps/frontend && pnpm install && pnpm run dev
```

または Docker 経由（ビルド済みフロントエンドを同じイメージにバンドルする）:

```sh
docker build -t lanrurugi .
docker run -p 3000:3000 -v /path/to/library:/library lanrurugi
```

新規インスタンス（またはパスワードを一度も変更していないレガシーインストールから移行した
インスタンス）は、レガシー LANraragi 自身のデフォルト管理者パスワードがそのまま有効な状態で
起動する。**初回ログイン後、設定ページから直ちに変更すること** — デフォルトパスワードのままの
インスタンスをローカルネットワークの外からアクセス可能な状態にしておかないこと。

### CLI サブコマンド

- `lanrurugi serve` — HTTP API、静的フロントエンド、ファイル監視、プラグインプールを 1 つの
  プロセスで実行する。
- `lanrurugi rebuild-index` — サイズを考慮したアルゴリズムですべてのアーカイブの ID を再計算し、
  過去の誤った統合によって隠されていた、それまで不可視だったファイルを発見する（User Story 6）。
- `lanrurugi bench` — 合成ライブラリを生成し、すでに稼働しているレガシーインスタンスに対して
  並行処理/スループットの比較を実行する（User Story 8。詳細は
  `specs/001-lanrurugi-full-rewrite/quickstart.md` の §8 を参照）。

## テスト

```sh
cargo fmt --all
cargo clippy --workspace --all-targets -- -D warnings
LANRURUGI_TEST_REDIS_URL=redis://127.0.0.1:16379 cargo test --workspace
```

Redis に依存するテストは、`LANRURUGI_TEST_REDIS_URL` が未設定の場合は正常にスキップされる。
実行するには、これを使い捨ての Redis インスタンス（例:
`docker run -d --rm -p 16379:6379 redis:7-alpine`）に向けること。

### フロントエンドテスト（`specs/003-ui-test-automation/`）

```sh
mise run test-frontend-unit   # Vitest + React Testing Library — 高速、バックエンド不要
mise run test-frontend-e2e    # Playwright — 実際のバックエンド + Redis、Chromium + Firefox
```

`test-frontend-e2e` はバックエンドをビルドしたのち、テストワーカーごとに独自の隔離された Redis
インスタンス、バックエンドプロセス、フロントエンドのプレビューサーバーを起動する
（`apps/frontend/tests/e2e/fixtures.ts` を参照）。常にクリーンな状態から開始する。1 回の実行に
限りティアダウンをスキップしてその後の環境（Redis/ライブラリの状態）を検査するには
`KEEP=1 mise run test-frontend-e2e` を設定する — これはその 1 回の実行を超えて永続することはない。
検証手順の全体については `specs/003-ui-test-automation/quickstart.md` を参照。
