设置 →「备份 / 还原」页把所有备份放在一处，分成三个标签：**快照**、**导入 / 导出**、**从 LANraragi 导入**。
本站其它文档说的「备份」在没有限定时，指的都是这里的快照。

## 两种备份，管的事情不一样

| | 快照（`.rdb`） | 导出（`.json`） |
|---|---|---|
| 存的是什么 | Redis 的全量数据文件 | 档案元数据、标签、分类、单行本、图章、书签 |
| 换机器能用吗 | 只对**同一个小版本结构**的库可靠，且必须整库替换 | 能，任意实例导入 |
| 能恢复什么 | 一切：连设置、令牌、阅读进度、搜索索引都回到快照时点 | 只有元数据，且只对「本库已存在的档案」生效 |
| 失败时能部分回退吗 | 不能，是整库替换 | 能，只覆盖记录本身 |
| 存放位置 | `<库>/.lanrurugi-backups/` | 同目录 |

快照就是 `redis-server` 自己 `BGSAVE` 出来的那份 RDB 的副本，所以它是「整个数据库的时间点」，
不是「一条条记录的列表」。

:::tip[选哪个]
想撤销一次误操作（清空档案、批量改标签）→ 快照。想搬到另一台机器、或只恢复标签分类 → 导出。
:::

## 自动计划

「快照计划」可以有多条，每条一个名字、一个 7 段 cron 表达式（`秒 分 时 日 月 星期 年`，年可留空），
各自按自己的节奏生成快照：

- 时间按**实例设置里的时区**解释，不是进程的 UTC。改成别的时区之后，同一条表达式会跟着落到新时区的
  那个钟点，不需要重写表达式。表单下的预设按钮覆盖了常见的几种节奏（每小时、每天 03:00、
  每周日、每月 1 日、每月第一个周日 `0 0 3 * * 0#1 *` 等）。
- 每条计划各留 N 份（`每个计划保留 [] 份`，默认 3）。**保留只在写入新备份时执行**：把数字改小不会
  当场删文件，多出来的那几份等下一次手动或自动备份时才被淘汰。
- 标了「保留」（图钉）的快照不参与淘汰，也不占名额。
- 第一条计划默认是「每周日 03:00」，可以改名、改表达式，或直接删掉。

## 在网页上还原

### 用快照还原（整库）

快照卡片第一个按钮就是「还原」。点开是一个列出后果的确认弹窗，需要**输入「还原」两个字**才能确认——
因为它替换的是整个数据集：

- 档案记录、标签、分类、书签、图章、搜索索引、**设置与登录状态**都会回到快照时点；
- 快照之后新增或修改的内容会丢失；
- 磁盘上的档案文件**不会被删除**，只是数据库里的记录回到旧状态（还原后跑一次扫描就能重新对账）；
- 还原期间站点会短暂不可用，完成后可能需要重新登录（快照里的登录令牌是旧的）。

还原过程有百分比进度条（走 SSE，和生成快照、导出、导入共用同一条通道），阶段会依次显示：
校验快照 → 生成 pre-restore 安全副本 → 替换 RDB → 重载 Redis 数据集 → 重写 AOF。

### 用导出还原（元数据）

「导入 / 导出」标签里每份导出的「恢复」按钮只覆盖元数据，属于可反复执行的轻量操作，确认一次即可。
恢复前同样会自动留一份 `pre-restore` 快照。

## 还原时正在发生别的事情怎么办

还原是**排他操作**，服务端会自己处理并发：

| 正在发生 | 还原时的行为 |
|---|---|
| 上传、下载入库、改标签、删档案（写请求） | 立刻拒绝，返回 `503 restore_in_progress`；读请求不受影响 |
| 已经进入处理流程的写请求 | 等它们写完（最多 30 秒）再替换数据集，超时会记一条警告 |
| 全库扫描、缩略图批量生成、重复档案检测、单行本归组分析 | 在下一个检查点（约每 200 条）发现还原进行中，就在**写数据库之前**中止，任务标为失败并提示「还原完成后请重新运行」 |
| 下载队列里正在下载的任务 | 入库那一步同样中止；已写到磁盘的文件留在原处，扫描会捡回来 |

这样设计的原因是：`DEBUG RELOAD NOSAVE` 会清空并重载整个数据集，窗口期内写进去的内容要么被丢掉，
要么落在一个「刚还原的旧世界」上（例如给已经不存在的档案写缩略图记录），事后很难分辨。

## 网页打不开时怎么还原

两条后路，都不需要打开网页。

### 容器内的命令行（推荐）

只要 Redis 还在跑就行——HTTP 服务挂了、前端报错、忘记密码，都能用：

```sh
# 列出快照（不需要 Redis 在线）
docker exec -it <容器名> lanrurugi-server snapshots list

# 还原某一份（会先打印将要做什么并等一次回车；--yes 跳过这一步）
docker exec -it <容器名> lanrurugi-server snapshots restore snapshot-20261124T065921Z-manual.rdb
```

它走的是和网页完全相同的那套逻辑：校验文件、先写一份 `pre-restore` 快照、原子替换 RDB、
`DEBUG RELOAD NOSAVE`、重写 AOF，进度直接打印在终端（每步后跟一句人话说明），最后打印
`restored …; previous state kept as <安全副本>`。原生安装包同理，把 `docker exec` 换成直接执行
`lanrurugi-server`。

用 `LANRURUGI_REDIS_URL` / `LANRURUGI_LIBRARY_PATH` 指定目标时可以不带参数；要显式传
`--redis-url` 之类的父级选项，得写在子命令**前面**（`snapshots --redis-url … restore <名字>`）。

### 纯 shell（连本程序都用不了）

只需要镜像里自带的 `redis-cli`。先确认 Redis 的数据目录与文件名，别猜：

```sh
docker exec <容器名> redis-cli -p 16379 CONFIG GET dir
docker exec <容器名> redis-cli -p 16379 CONFIG GET dbfilename
docker exec <容器名> redis-cli -p 16379 CONFIG GET appendonly
```

然后把快照复制成 Redis 正在用的那份 RDB，让它重新加载，再把 AOF 重写成一样的内容：

```sh
# <dir> / <dbfilename> 换成上面查到的值（容器内路径）
docker exec <容器名> cp "/home/koyomi/lanrurugi/content/.lanrurugi-backups/<快照文件名>" "<dir>/<dbfilename>"
docker exec <容器名> redis-cli -p 16379 DEBUG RELOAD NOSAVE
docker exec <容器名> redis-cli -p 16379 BGREWRITEAOF
```

`DEBUG RELOAD NOSAVE` 是让运行中的 Redis 重新读取磁盘上的 RDB 的唯一无损办法 —— 注意必须带
`NOSAVE`：不带的话 Redis 会先把**当前内存**数据集写回 RDB 再加载它，等于把刚复制进去的快照覆盖掉
（这一点在 8.2.1 上实测过，值仍然是还原前的新数据）。镜像自带的 `redis.conf` 里已经打开
`enable-debug-command local`（只接受本机回环连接）；如果你用的是**外部** Redis，需要自己在它的配置里
打开这一项，否则网页/CLI 还原会返回 `debug_command_disabled`（409，已自动回滚，不会损坏数据），
shell 这条路则会得到 `DEBUG command not allowed`。

:::caution[AOF 必须重写]
镜像默认 `appendonly yes`。只替换 RDB 而不 `BGREWRITEAOF`，当前进程看起来是旧数据，但下一次重启
Redis 会从 AOF（还是新数据）恢复，等于什么都没做。同理，手工还原前最好先 `docker exec <容器名>
redis-cli -p 16379 BGSAVE` 存一份当前的 RDB 作为退路。
:::

## 常见问题

**还原后需要重新登录？** 会。快照里带的是当时的会话与令牌，还原之后当前会话可能已经不存在了。
用管理员密码重新登录即可。

**快照删不掉？** 最新一份可用的快照受保护，删除会返回 `409 last_usable`。先点「立即生成快照」生成一份
更新的，再删旧的；或者直接把它标成「保留」留作长期基线。

**还原后档案数量对不上？** 数据库回到了快照时点，磁盘上的文件没动。跑一次全库扫描，把「磁盘上有、
数据库里没有」的档案重新登记回来；「数据库里有、磁盘上没了」的记录会在下一次数据库清理里被清掉。

**能只还原某一个档案吗？** 不能。快照是整库时间点，没有记录级的回滚。要撤销单个档案的改动，用它的
编辑页面或标签历史，不要用快照。
