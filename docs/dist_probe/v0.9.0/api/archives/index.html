批量删除档案（DELETE /archives，请求体 {ids: [...]}）

Section titled “批量删除档案（DELETE /archives，请求体 {ids: [...]}）”
DELETEhttp://localhost:3000/api/archives

尚未在此参考中描述。这个端点会被列出，是因为服务端确实注册了它，但它的请求与响应形状还没有写下来。

下面这段是 handler 自己的文档注释（crates/lanrurugi-api/src/archives.rs:618）的译文；原文以源码为准。

DELETE /archives（issue #63），请求体 {ids: [...]}——沿用本代码库已有的「复数资源 + 用 JSON 请求体指明操作对象」这一形态（见 activity.rs::bulk_delete_activity 的 DELETE /activity），而不是 POST .../batch-delete 那种动作式路径；按 RFC 9110，DELETE 可以带请求体（虽然一些较旧的代理/客户端在实践中会静默丢掉它，但 Axum 和本项目自己的前端都处理得很好，而且本仓库已有先例）。Batch 页面自己的「删除档案」操作此前是在前端按选中的档案逐个发 DELETE /archives/{id}，就是一个普通的顺序循环（没有原子性，没有统一的审计点，而且——由于每个请求只报告自己的成功/失败——调用方除非在操作前后对比整个书库，否则无法知道哪些 id 失败了）。这里把同样的逐 id 工作（delete_one_archive，与单条删除端点完全相同的清理）放到服务端一个请求里完成，并返回逐 id 的结果列表，让前端能准确展示发生了什么，而不是假定全部成功。

仅限会话调用（route_policy.csv 拒绝所有令牌角色以及 anonymous）——刻意比本文件里其他所有会修改档案的端点都更严格，那些端点 Token（Admin 或 Guest）都能调用。一个泄露或被写错的 API 令牌就能在一个请求里抹掉任意规模的库内容，其影响范围远大于令牌访问本来就允许的任何一个单目标端点；而本项目对批量删除并不存在像脚本化上传或元数据编辑那样的正当自动化场景——所以这条额外限制不会破坏任何真实工作流。

响应

200该端点已响应；其确切结构尚未记录，见 crates/lanrurugi-api/src/archives.rs:209 处的 handler。

该响应没有示例数据。

该端点只接受网页会话（登录本站所用实例后浏览器自动携带的 cookie）。API 令牌会被服务端拒绝，因此这里不提供令牌输入框，上面的命令行也不带 Authorization 头。

请求失败 — 常见原因：实例地址填错或不可达；实例未开启「为客户端 API 启用 CORS」；或者文档站是 HTTPS 而实例是局域网内的纯 HTTP（浏览器按混合内容拦截）。可以用上面的「复制为 cURL」在终端里发同样的请求。

Start or re-attach to a resumable upload
Section titled “Start or re-attach to a resumable upload”


POSThttp://localhost:3000/api/archives/upload/session


Creates a session (an empty staged file plus a sidecar describing it) and returns the id. If
client_key matches a session that is still alive, that session is returned instead, with the
offset its bytes are already at — which is what makes a page refresh resumable rather than
restarting the transfer.


The returned offset is always read from the staged file’s real length, never from the
sidecar, so a truncated or edited sidecar cannot make the server believe it holds bytes it
does not.


Sessions that have not been touched for 24 hours are swept by the operations here; the staged

Append one chunk
Section titled “Append one chunk”


PUThttp://localhost:3000/api/archives/upload/session/{id}


Appends the request body to the staged file, but only at the position the client claims.
Upload-Offset is required and must equal the staged file’s real length; the response always
reports the authoritative offset, including on failure:


    

  • 204 — the chunk was appended; Upload-Offset is the new length.
    • 

  • 409 — the client’s offset disagrees with the disk (a lost response, a retried chunk, two
tabs); Upload-Offset says where to resume from.
    • 

  • 400 — missing or malformed Upload-Offset.
    • 



A connection that dies mid-chunk keeps whatever bytes reached the disk and reports the offset,
so a partial chunk is just fewer bytes rather than a corrupt one. The body is bounded at 64
MiB (the one-shot route is deliberately unbounded; a chunk is supposed to be small).

Finish a session and ingest it
Section titled “Finish a session and ingest it”


POSThttp://localhost:3000/api/archives/upload/session/{id}/complete


Verifies what landed, hashes it, and hands it to the same ingest the one-shot route uses —
including the persistent download-queue row, so a completed upload shows up (and can be
removed) exactly like any other queue item.


Verification: a file_size announced at session creation must equal the staged length
(417 otherwise, and the staged bytes are dropped), and an optional file_checksum is
compared against the SHA-1 of the finished file (417 on mismatch). That SHA-1 is computed by
reading the staged file once at this point rather than persisting incremental hasher state:
a resumed upload’s early chunks were hashed by processes that are long gone, and state that
can silently desync from the bytes on disk is a worse trade than one sequential read of an
already-local file.


After this call the session no longer exists.
