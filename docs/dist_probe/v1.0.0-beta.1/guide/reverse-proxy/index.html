反向代理

LANrurugi 本身只提供 HTTP（默认端口 3000，同时监听 IPv4 和 IPv6）。要通过域名和 HTTPS 访问，在它前面放一个反向代理。 无论用哪一种代理，都要满足下面几条。

下面的例子都按默认的 3000 写。如果你改了监听地址（--bind / LANRURUGI_BIND，见安装与 原生安装），所有 127.0.0.1:3000 要跟着改。

代理需要满足的条件

Section titled “代理需要满足的条件”
  • 挂在域名根路径下。 前端以绝对路径 /api/... 请求接口，不支持挂在子路径（如 example.com/lanrurugi/）下。请用独立的域名或子域名，例如 manga.example.com。
  • 转发三个请求头。 X-Forwarded-Proto（判断是否走 HTTPS）、X-Forwarded-Host（跨域登录交接与 OpenSearch 生成正确的地址）、X-Forwarded-For（活动记录里显示真实客户端 IP）。同时保留原始 Host。
  • 不要缓冲 SSE。 下载队列进度、AI 插件向导与拆包建议使用 Server-Sent Events 实时推送。代理一旦缓冲 响应，这些界面就会卡住、直到请求结束才一次性刷新。服务端每 15 秒发送一次心跳，所以默认的读超时 （通常 60 秒）够用，但缓冲必须关闭。
  • 放开上传大小。 档案上传以每片最多 64 MB 分片发送，旧版数据导入单次最多 100 MB。代理的请求体 上限要不小于这个值，最简单的做法是不设上限。
  • 走 HTTPS 后打开安全 Cookie。 在 compose 里设置 LANRURUGI_FORCE_SECURE_COOKIES=true。服务端不会 根据 X-Forwarded-Proto 自动推断这一项——那个请求头可以被伪造，而本服务没有可信代理白名单。只走 HTTP 时不要打开它，否则浏览器会丢弃登录 Cookie，导致无法登录。

不需要 WebSocket。

下面的示例都假设 LANrurugi 与代理在同一台机器上，监听 127.0.0.1:3000；如果代理和 LANrurugi 在同一个 compose 网络里，把地址换成 lanrurugi:3000。

检查是否配置正确

Section titled “检查是否配置正确”
  1. 打开 https://manga.example.com，能正常登录且刷新后仍保持登录。
  2. 在下载队列里添加一个任务，进度条应当连续推进，而不是在结束时才一次跳到 100%。
  3. 活动记录页（/activity）里，登录记录显示的是你的客户端 IP，而不是代理的地址。
